# 01 · 调研文档

> 目标：在动手前确认「跨智能体能力中枢」这个形态是否有人做过、做到什么程度、哪些部分值得借鉴、哪些坑必须避开。
> 调研方式：检索同类开源项目 README 与规范文档，逐条对照本项目需求做取舍判断。

---

## 1. 同类项目对照

| 项目 | 形态 | 做了什么 | 关键差异 / 我们不该照搬的地方 |
| --- | --- | --- | --- |
| SkillsHub | npm-for-Agent-Skills | 技能发布/搜索/版本/安全扫描，SQLite FTS5，MCP server | 只覆盖 Skill 一类，且是**发布中心**（npm 语义）。我们覆盖 Skill/MCP/Plugin，且以**本机已安装资产**为一等公民 |
| TARS | Tauri 桌面 | 管理 Claude Code 的 skills/agents/commands/hooks/MCP/plugins，带项目维度与 profile 市场 | 强绑定 Claude Code 单一生态；有「collision detection」但只是提示冲突，没有裁决与归档闭环。我们把它扩成跨宿主 + 可执行裁决 |
| agent-hub | Tauri 桌面 | 统一管理 Codex/Claude/Cursor/Antigravity 等的 Skill 与 MCP，含会话、监听、账号用量 | 覆盖面广，但定位是「管理面板」：读配置、展示、启停。**没有统一能力模型、没有检索、没有维修** |
| agentdesktop | 设备侧守护进程 | 发现 AI 工具、盘点 MCP/skills、按各工具原生格式下发配置、接 LLM 网关 | 面向企业 fleet 治理，强在「配置意图 → 原生格式翻译」；我们是单机个人中枢，更重检索与修复。其「dry-run 预览」思路值得借鉴（我们做成导入预检 + 同步预览） |
| MCP 官方规范 | 协议 | 工具/资源/提示词、stdio 与 Streamable HTTP 传输 | 直接适配，不重造。注意 2025-06-18 版本号为当前主流 |
| Agent Skills 规范 | 协议 | `SKILL.md` + frontmatter（name/description/license/allowed-tools） | 直接适配 |

## 2. 关键结论（决定了本项目的形态）

1. **「索引 + 展示」的项目已经很多，能「修」的几乎没有。**
   TARS 只做 collision detection，agent-hub 只做启停，SkillsHub 只做发布。
   因此本项目把差异化放在**诊断 → 定位 → 派单 → 补丁回传 → 验证**这条闭环上，
   并且严格遵守「中枢只诊断，修复由智能体执行」的职责边界。

2. **跨宿主的难点不是读取，而是归一。**
   同一个 `pdf` 技能在 MiniMax、Codex、DSH 里各存一份，名字相同、版本不同、作者缺失。
   必须建立「逻辑能力（capabilities）+ 物理实例（installations）」两层模型，
   否则检索结果会被同一能力的多个副本淹没，去重也无从谈起。

3. **中文检索是硬需求，而 SQLite 原生不支持。**
   `unicode61` 分词器把整段中文当一个 token，`trigram` 也不切汉字。
   实测（见测试文档）证明：入库前对 CJK 逐字加空格，索引与查询两侧一致即可命中。
   这比引入外部分词服务（jieba、ICU）更稳、零依赖。

4. **不要重造协议执行层。**
   MCP 已经有标准传输与工具语义，我们只实现 server 侧，把「能力执行」留给宿主。

5. **更新检查必须能离线工作。**
   上游包的兼容性缓存就在本机；逐个打 npm registry 会非常慢（300+ 能力串行实测超过 4 分钟仍未完成）。
   结论：**缓存优先 + 可选联网 + 并发检查**。

6. **「已有能力」和「能拿到但没装的能力」是两回事。**
   前者是能力库（已纳管），后者是目录（可获取）。两者必须分表存储，
   否则「已安装 / 可更新」的判断会彻底混乱。

7. **云端模型是增强，不是依赖。**
   引入向量检索与精排能显著提升中文语义召回，但一旦云端不可用就不能让检索瘫痪。
   因此设计为「云端优先 + 本地兜底 + 明确标注本次走了哪条路」。

## 3. 调研方法说明

对照的同类项目均为公开仓库，取其 README 与规范文档中描述的能力清单逐条比对，
不做代码级借鉴；本项目实现为独立编写。
