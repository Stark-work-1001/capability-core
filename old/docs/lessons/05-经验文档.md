# 第一部分：踩坑与解决方案

## P01 — Rust 枚举偏序缺 `PartialOrd`

**现象**：`cargo build` 报 `E0369: binary operation '>' cannot be applied to type 'ToolPosture'`。

**原因**：我在 `identity.rs` 里用 `self.side_effect < required.side_effect` 做委派链权限比较，
但 `SideEffect` 和 `ToolPosture` 只派生了 `PartialEq, Eq`，没有 `PartialOrd`。
`Authority` 我写对了（因为它确实需要排序），另外两个漏了。

**解决**：给两个枚举补 `PartialOrd, Ord`。`Authority` 已有，补齐后一次性通过。

**教训**：Rust 的派生属性是**逐个枚举**独立声明的，没有"整个文件统一"的概念。
以后写一组需要互相比较的枚举，建议统一在一个 module 里声明，方便 review。

## P02 — rustup 已存在但 PATH 未生效

**现象**：`cargo --version` 报找不到命令，但 rustup-init 提示
`warn: it looks like you have an existing rustup settings file at C:\Builds\PublicUser01\.rustup\settings.toml`。

**原因**：机器上**曾经装过 Rust**，但当前 shell 的 PATH 没有 `~/.cargo/bin`，
所以看起来像"没装"。rustup-init 检测到旧配置后走了"更新"路径，从 1.99.0 升到 1.99.1。

**解决**：装完后在当前会话手动 `$env:PATH = "$env:USERPROFILE\.cargo\bin;$env:PATH"`。
长期方案：新开的终端会自动生效。

**教训**：报"未安装"之前先查 `~/.rustup/settings.toml` 和 `~/.cargo/bin`，
可能只是 PATH 问题，跳过安装反而更安全。

## P03 — 资产拷贝未排除依赖目录，体积失控 100 倍

**现象**：`robocopy /E` 拷贝 `.plugin/` 时，13 个插件就吃了 **3.7 GB**，而且拷了 10 分钟没完。

**原因**：`.plugin` 里的插件目录**内嵌了完整的依赖树**：

| 膨胀源 | 实际情况 |
|---|---|
| `node_modules` | pnpm 结构，`dsh-agent-swarm\node_modules\.pnpm\` 下嵌套数千包 |
| `.git` 仓库 | `plugin-hub-plugin\.work\acceptance-repo-*\` 内有**数十个内嵌 .git 仓库** |
| `__pycache__` | Python 字节码 |

单个最大插件 `dsh-mnemon` 778 MB。

**解决**：
1. 中止首轮拷贝
2. 加排除列表 `/XD node_modules .venv venv __pycache__ .git target .cache .next .turbo .pytest_cache`
3. 干净重做

**根本教训**：**注册/索引场景不需要运行时依赖。**
CapabilityCore 只需要 manifest 文件和目录结构来建索引，拷贝 node_modules 是纯浪费。

**建议（已采纳）**：vendor 采用"**清单式拷贝**"策略——只拷元数据文件，
不拷任何可再生依赖。后续若需实际运行某个插件，再按需单独安装其依赖。

## P04 — 回收站无法处理超大目录

**现象**：`rm -- "D:\...\vendor\plugin"` 报
`Permission denied for bash: Blocked: dangerous removal target` 和
`failed to trash ... #< CLIXML`。

**原因**：两层问题——
1. 首次调用时 PowerShell 变量 `$pluginCopy` **没有被展开**，被当作字面字符串传给了回收站包装器
2. 改用字面路径后，反斜杠被吞掉，路径被拼成一串粘连的字符串（各段分隔符全部丢失）
3. 3.7 GB 目录本身就超出了回收站的处理能力

**解决**：
- 变量问题：传字面路径，不传变量
- 反斜杠问题：改用正斜杠 `C:/external-assets/...`
- 体积问题：回收站仍然失败，改为 **`Move-Item` 重命名让路**，把旧目录挪到 `_legacy_bloated`，
  在原位置做干净拷贝

**建议**：`vendor/` 这类可再生成的目录，其实不值得进回收站。
更好的做法是**一开始就用排除列表**，避免产生需要删除的垃圾。

## P05 — `notifications/tools/list_changed` 在主流客户端是空转的

**来源**：调研阶段发现，非本次开发踩的坑，但直接决定了架构。

**现象**：MCP 服务端发送 `notifications/tools/list_changed` 后，
Claude Code **不会重新拉取工具列表**，也不把新 schema 注入上下文，通知被静默忽略。
Cursor CLI 同样。Cline 的 core runtime 直到 2026-10-08 才在 PR #14946 补上刷新逻辑。

**为什么重要**：如果 M2/M3 依赖"服务端推通知、客户端刷新"来做动态挂载，在多数客户端上会静默失败。

**解决**：M2/M3 的动态挂载**不依赖 list_changed**，改用显式 meta-tool
（借鉴 Docker MCP Gateway 的 `mcp-find`/`mcp-add`/`mcp-exec`），让 agent 主动调。

## P10 — id 用「叶目录名」，78 个资产被静默覆盖

**现象**：首次对 `vendor/` 跑入库，磁盘上 508 个清单文件，库里只有 427 个，**不报任何错**。

**定位**：`.qoder-plugin` 目录名被 **22 个不同插件**共用 → 全部映射到 `plugin::.qoder-plugin`。
`.claude-plugin` ×4、`.codex-plugin` ×3、`.zcode-plugin` ×3 同理。
另外 `skill::astropy` 这类，父包里带了 `references/scientific-skills/astropy/` 的镜像副本。

**根因**：id 取「清单文件所在目录名」，而目录名在真实资产里根本不是身份——
`.qoder-plugin` 是**清单存放位置的约定名**，不是插件标识。

**解决**：id 改为 `<kind>::<相对扫描根的目录路径 slug>`。
`.qoder-plugin` → `qoder-plugin`，路径逐段拼接后天然唯一。
同目录多份同类清单（`.mcp.json` + `mcp.json`）再追加 6 位短哈希消歧，
且**冲突组全体都打标签**，保证以后往该目录加文件不会改动已有 id。

**教训**：**任何用文件名/目录名当主键的设计，都要先拿真实数据跑一遍再定稿。**
合成 fixture 里 `s1` `s2` 这种名字永远不会暴露这个问题。

## P11 — `slugify` 把中文目录名整个吃掉

**现象**：修完 P10 后仍有 17 个资产丢失。

**定位**：`slugify` 原本只保留 ASCII 字母数字，
`skills/产品指标复盘/` 这一整段被压成空串然后丢弃，
于是 7 个不同中文技能全部落到 `skill-product-management-1-1-1-skills`。

**解决**：改用 `char::is_alphanumeric()`（Unicode 感知），保留中文。
`skills/产品指标复盘` → `skills-产品指标复盘`。
SQLite / JSON / Tauri 都能直接吃 UTF-8，为了"看着像 slug"而丢信息没有道理。

**教训**：为"生成好看标识符"写的规范化函数，**默认会误伤非常规字符**。
中文、日文、emoji、带空格与标点的目录名都要显式测试。

## P12 — 跳过目录的检查误用了绝对路径

**现象**：scan 测试全部返回空，且报 `PermissionDenied (os error 5)`。

**第一层误判**：先以为是并行竞态（多个测试共用同一个临时目录名，一个删一个建）。
改成每测试唯一目录后仍然报同样的错——说明根因不在竞态。

**第二层误判**：又以为是路径权限问题。写了个 rustc 探针程序逐个目录试：
`%TEMP%` / `%USERPROFILE%` / `C:\` / `D:\` 全部拒绝创建，但 `C:\external-assets\...` 可以。
**同一个路径用 PowerShell / cmd / Python 建却都成功**——只有 Rust 进程被限制。
这是执行沙箱的路径白名单，与代码无关。

**真根因**：测试临时目录建在 `<target>/release/…` 下，
而跳过列表里就有 `target`。跳过检查作用在**整条绝对路径**上，
于是整棵树被当成依赖目录跳过，一条不扫。

**解决**（两处都要改）：
1. 跳过检查改用 `path.strip_prefix(root)` 的**相对路径段**
2. 测试临时目录不再用 `std::env::temp_dir()`，改锚在 `target/` 下
   （`CARGO_TARGET_TMPDIR`，单元测试拿不到就由 `current_exe()` 反推）

**教训**：
- 写"路径包含 X 就跳过"这类逻辑时，一定要问一句：**X 是相对于谁的？**
- 同一个操作在不同进程里表现不一致时，先怀疑宿主环境，
  用最小探针程序把边界测出来，再回头看代码——否则会一直在错误的方向上改。

## P13 — `CREATE TABLE IF NOT EXISTS` 让首次升级必崩

**现象**：给 `assets` 表加了几列之后，老库直接打不开：
`no such column: authority in CREATE INDEX ...`。

**根因**：`CREATE TABLE IF NOT EXISTS` 在表已存在时**静默跳过**，
于是新列不存在，紧接着的 `CREATE INDEX` 就炸。
这个错**只在用户第一次升级时**发生——开发期因为总是新建库反而看不见。

**第二层坑**：加 `PRAGMA user_version` 记录版本号后仍然崩。
因为**早期版本从来没写过 `user_version`**，真老库的版本号也是 `0`，
按 `0 == 全新库` 处理照样跳过建表。

**解决**：迁移逻辑**以实际列形状为准**（`PRAGMA table_info`），
版本号只用来发现"库比程序新"这一种情况：
```
建表(IF NOT EXISTS 幂等) → 逐列检查并 ALTER → 回填 → 最后建索引
```
**索引必须放最后**，因为它依赖刚补上的列。

**关键细节**：补完列必须**回填**。
增量写入时内容没变的行走 "unchanged" 分支只刷 `last_seen`，
不回填的话这些行会永远停在默认值，且不报错。

**教训**：schema 演进不能只靠 `IF NOT EXISTS`。
而且"没有版本号"和"版本号是 0"是**两件不同的事**，前者更常见。

## P14 — 改了解析逻辑，老资产却永远不刷新

**现象**：修完 MCP 展示名（`0.1.1` → `presentations`）后重新入库，
报告是 **508 全未变化**，新逻辑完全没生效。

**根因**：增量判定只看 `content_hash`，而那是**源文件字节的指纹**。
源文件一个字没改，解析器改了也不会被察觉。

**解决**：引入 `PARSER_REV` 常量参与判定——
`content_hash` 相同 **且** `parser_rev` 相同 才算 unchanged。
改解析/推断逻辑时 `PARSER_REV += 1`，下次入库自动全量重写。

**教训**：**内容哈希只能回答"源文件变没变"，回答不了"我的理解变没变"。**
凡是"用旧数据缓存算出来的结果"，就必须同时记录生成它的那版代码，
否则改进永远落不了地，而且没有任何症状。

## P15 — 厂商把组件声明成路径字符串

**现象**：36 个 plugin 里有 22 个能力数为 0，在界面上等于不存在。

**定位**：qoder / cursor 格式的清单写的是
```json
{ "name": "qgraphflow", "skills": "skills" }
```
`skills` 是**字符串**（指向同级目录），不是数组。
解析器只认数组和对象，字符串直接跳过。

**解决**：三种写法都认——数组、对象（`hooks: {PostToolUse: []}`）、字符串。
字符串写法如实记下声明位置并建立 `Requires` 关系，
组件内容展开留给 M2 的组件解析器（**解析阶段不做 IO 是刻意的边界**）。
修复后零能力插件从 22 降到 19。

**剩下 19 个**是 `.claude-plugin/plugin.json` 根本不内联声明组件，
内容在同级 `commands/` `agents/` `skills/` `.mcp.json` 目录里。
那些组件已经作为独立 Skill / MCP 资产入库了，缺的是"插件→组件"的归属关系。

**教训**：真实世界的配置格式**同一语义会有多种编码**。
把"没见过的写法"当错误处理，等于主动丢弃数据；宽容解析 + 如实记录更安全。

## P16 — 枚举序 ≠ 字符串字典序

**现象**：`min_authority = "write"` 的过滤结果为空或反了。

**根因**：`Authority` 的枚举升序是 `read < observe < write < destructive`，
而这些字符串的字典序是 `destructive < observe < read < write`——
**两者几乎完全相反**。直接 `WHERE authority >= ?` 会得出荒谬结论。

**解决**：SQL 里用 `CASE` 把字符串映射成等级再比：
```sql
CASE a.authority WHEN 'read' THEN 0 WHEN 'observe' THEN 1
                  WHEN 'write' THEN 2 ELSE 3 END >= ?
```
Rust 侧同样显式映射，不用字符串比较。

**教训**：把枚举**存成字符串**换来了可读性和可手查，
代价是排序与比较必须显式映射。凡是"存了字符串还要比大小"的地方，
都要在测试里放一个**反直觉的值**（比如 `destructive`）来验证方向没搞反。

---

## P17 — 并行测试共用临时目录

**现象**：多个 scan 测试随机报 `PermissionDenied` 或结果为空。

**原因**：`cargo test` 多线程并行，所有测试用
`temp_dir()/ac-scan-test-{pid}`——pid 相同，于是共用一个目录。
一个测试 `remove_dir_all` 的瞬间另一个正在 `create_dir_all`。

**解决**：`testutil::Scratch` 用**原子计数器 + 标签**生成唯一目录，
并实现 `Drop` 自动清理（测试 panic 也不会留下垃圾）。
顺带解决了 P12 的"系统 TEMP 不可写"。

**教训**：测试夹具的**唯一性**和**生命周期**是两件事，缺一不可。
`Drop` 清理比在测试结尾手动 `remove_dir_all` 可靠——
断言失败时手动清理那行代码根本执行不到。

# 第二部分：功能提升与建议

> 这一部分是本文档的**重点**。以下按优先级排列。

---

## S01 【最高】L4 身份维度要能在 UI 里可视化编辑

**现状**：`CapabilityIdentity` 的 `dimensions` 是 `BTreeMap<String,String>`，
由 M1 的推断器自动填充。

**问题**：推断必然有误。用户需要能**看见**每个资产被推断成了什么身份，
并**手动纠正**——比如把某个被误判为 `destructive` 的工具改成 `read_only`。

**建议**：
- M1 UI：资产详情面板展示身份维度，支持点击编辑
- 手动修改的维度**覆盖**自动推断，并标记 `source: manual` 防止下次扫描被覆盖
- 提供「重置为推断值」按钮

**价值**：这是身份维度能不能真正用起来的关键。不可见、不可改的自动推断等于没有。

---

## S02 【最高】检索路径要可视化，让用户知道结果怎么来的

**现状**：M3 四级瀑布（全文→向量→融合→LLM）对用户是黑盒。

**建议**：每条检索结果标注命中的层级，并可展开查看：

```
🔵 查询：「把这个表格转成 CSV」
   ├─ ① 全文匹配：命中 2 项（工具名含 "csv"）
   ├─ ② 向量语义：召回 5 项（余弦相似度 0.72~0.88）
   ├─ ③ 融合排序：RRF 加权后 Top 3
   └─ 结果：convert_table_to_csv  [来源②]
```

以及**降级提示**：
```
⚠ 向量服务不可用，已降级为全文检索，结果可能不完整
```

**价值**：可信度。检索系统最大的用户痛点不是"找不到"，而是"不知道它凭什么这么找"。

---

## S03 【高】增量索引要能在运行时安全触发

**现状**：`Provenance.content_hash` 已预留，变更检测在 M1 实现。

**建议**：
- 提供三种触发方式：手动按钮 / 文件系统 watcher / 定期轮询
- **关键约束**：扫描时**只读** `vendor/`，绝不能修改源目录
- 索引重建期间旧索引仍可用（读写分离，先建新索引再原子切换）

**风险提示**：文件系统 watcher 在 Windows 上对大量小文件可能不稳，
需要降级到轮询。建议默认轮询，watcher 作为可选项。

---

## S04 【高】MCP server 要支持能力热更新而不重启

**背景**：见 P05，`list_changed` 不可靠。

**建议**：
- 智能体每次调用 `tools/list` 时实时返回当前能力集，不缓存
- 同时提供显式 `refresh()` 方法供客户端主动调用
- 内置一个 `capability_search` meta-tool，让 agent 自己找能力，
  而不是等中枢把几百个工具塞进上下文

**价值**：这是本项目区别于普通 MCP gateway 的核心特征，必须做到无缝。

---

## S05 【高】MCP 要从一开始就支持多智能体

**现状**：需求 2 和 8 明确要求多智能体协同与共享工具协调。

**建议**：不要做成"M1 单智能体，M5 再加多智能体"。**M1 就要把 `agent_id` 设计进所有查询接口**。

具体：
- 所有索引查询带 `agent_id` 参数（M1 可以先传固定的单值）
- `CapabilityIdentity` 的裁剪从第一天就走 `admits()`
- 工具池设计成**共享实例 + 能力视图**，而不是每个智能体一套

**否则**：M5 会出现"所有数据结构都要加 agent 字段"的破坏性重构。

---

## S06 【中】M4 要支持云端与本地的成本感知路由

**背景**：你明确说了——本地模型 token 慢、占资源会卡顿，需要多云端方案作为备选。

**建议**：路由不只是"本地 vs 云端"二选一，应引入**成本与延迟的联合决策**：

```rust
enum RoutePolicy {
    AlwaysLocal,           // 纯离线
    PreferLocal,           // 本地优先，超时才降级
    PreferCloud,           // 云端优先（默认，响应快）
    CostOptimized,         // 按任务复杂度选
}
```

配套：
- 记录每个 provider 的历史 P50/P95 延迟
- 任务类型标记（如"简单分类"走本地，"复杂规划"走云端）
- **熔断**：某 provider 连续失败 N 次自动切换

**价值**：避免"一键切到云端"导致成本失控，也避免"永远本地"导致卡顿。

---

## S07 【中】Plugin 层格式要尽早定稿

**现状**：M1 解析三种格式（SKILL.md / plugin.json / .mcp.json），但输出统一格式。

**建议**：M1 结束时产出 `proto/capability-manifest-v1.yaml`，
**并在 v0.2.0 冻结**。理由：这是全项目唯一有"标准"属性的产物，
一旦下游开始用，格式变更成本极高。

**同时建议**：支持"从现有格式反向生成"——读 plugin.json，产出 manifest，
再由 manifest 生成 plugin.json。让中枢成为格式转换器，而不只是索引器。

---

## S08 【中】向量层要有独立的可用性探测

**现状**：M3 会引入 MiniLM（ONNX）。

**建议**：
- 嵌入模型**进程内常驻**，不要每次调用加载（否则延迟会难看）
- 但常驻会占内存 —— 提供 `lazy` / `eager` 两种预热模式
- 健康检查独立于检索路径，模型加载失败要**立即**降级而不是等查询超时

**风险**：ONNX runtime 在某些受限企业环境可能装不上。
要准备纯 CPU 的 fallback 实现（同样的 MiniLM 权重，用更轻的推理后端）。

## S09 【低】为"空结果"设计明确行为

**建议**：检索不到时，**不要返回空列表**。应该：
1. 放宽过滤条件重试（如去掉 tag 约束）
2. 返回"最接近的 3 个"并标注"这些不完全匹配，你要的是不是……"
3. 给出建议（"当前索引只有 Skill 类能力，MCP server 尚未接入"）

**价值**：空结果是最糟糕的 UX，用户不知道该换查询词还是该换工具。

## S10 【低】预留 Ghost 与 Suite 的实例形态

**现状**：`ghost/`、`suite/`、`organization/` 三个源目录都是空的。

**建议**：在 M1 设计 Manifest 时就为这三类留出实例，即使现在没有。
特别是 `Ghost` —— 它没有实体工具，只在委派链中存在。
如果等到有实例才设计 schema，多半会推倒重来。

**理由**：这三类恰恰是本项目区别于普通 MCP gateway 的地方，不能因为"现在没数据"就往后推。

## S11 【高】推断结果必须标来源，且推断错要能一键纠正

**M1 现状**：身份推断已经跑通（`infer.rs`），资产详情面板已经能展示
`authority / side_effect / tool_posture / role / 推断维度`。
但**只能看，不能改**。

**实测暴露的问题**：508 个资产里 **445 个落在最低权限 `read`/纯计算**。
技术上完全正确（这些 Skill 的 frontmatter 没声明 `allowed-tools`，
按"拿不准就收紧"的设计保持最低），但对用户来说就是"508 个资产里只有 63 个能用"——
第一眼会以为注册器坏了。

**建议**：
1. 每条推断维度标注来源：`自动推断` / `人工指定`
2. 支持人工覆盖，被覆盖的字段写进 `manual_identity=1`，
   后续扫描**不覆盖**人工值（schema 里这个列已经预留好了）
3. 详情面板提供「重置为推断值」
4. **在资产列表上区分「声明过权限」与「未声明，按最低处理」**——
   这是两种完全不同的状态，不该长得一样

**价值**：不可见、不可改的自动推断等于没有（S01 的延续）。
而且"没声明"和"声明成只读"必须让人一眼分清。

## S12 【高】把"重复内容"显式暴露出来，别让用户自己撞

**M1 现状**：`vendor/` 里存在**同包多副本**——
`codex-claude-academic-skills-main/scientific-toolkit-skill/references/scientific-skills/astropy/`
和 `scientific-toolkit-skill/references/scientific-skills/astropy/` 下有内容完全相同的 `SKILL.md`。
M1 按路径各注册一条（id 唯一优先），用户会在列表里看到重复项。

**建议**：
- 入库时按 `content_hash` 分组，统计"内容重复的资产组数"
- 界面上给重复项打标，可一键折叠成"一个条目 + N 个位置"
- **不要静默去重**：同一个技能装在两个位置可能是用户的**有意为之**
  （比如给不同 agent 准备不同版本），静默合并会丢掉这个意图
- 让用户选「全局保留一份」还是「按位置分别保留」

**价值**：这是导入类产品最常见的困惑来源。
把选择权交给用户，比替他做决定安全得多。

## S13 【中】扫描吞吐 34 项/秒，需要在 M2 前后重新评估

**M1 实测**：508 个资产全量扫描约 15s，约 34 项/秒，**低于 200 的规划目标**。

**拆解**：时间主要花在遍历 800MB 的 vendor 树 + 508 次文件读 + SHA-256。
不是 SQLite 慢（入库本身很快）。

**建议**：
- M2 引入 tantivy 后，扫描与索引**分离**：扫描只产出 manifest 变更事件，索引由索引层消费
- 日常走增量（M1 已经是了），全量扫描只在用户点「重新扫描」时发生
- 目录遍历用 `ignore` crate 替代手写 `walkdir`，能吃到 `.gitignore` 语义
- 若仍不够，考虑**文件系统监听**（`notify`）替代轮询

**判断**：15 秒对 508 项的首屏是可接受的（配合异步不挡 UI），
但资产量上到几千后会成为问题。**M2 结束时必须复测这个指标。**

## P18 — MSVC 14.44 debug 构建坏，强制走 `--release`

**现象**：`cargo test -p ac-registry`（默认 debug）`cc-rs` 调 `cl.exe` 报
`D8050：无法执行 c1.dll —— 未能将命令行放入调试记录中`。

**根因**：BuildTools 14.44.35207 的 `c1.dll` 在这台机器上生成调试记录失败。
**`cargo build --release` 完全正常**，差异只在生成 PDB。

**规避**：所有 cargo 命令统一带 `--release`。
后续在 CI 里加一条 `cargo build`（debug）做兜底，release 实测正常时不算回归。

**价值**：少让人花 10 分钟怀疑代码。

## P19 — 「前导 `_` / `.` 当通用隔离规则」两个方向都翻车

**现象**：第一版用 `seg.starts_with('_') || seg.starts_with('.')` 隔离。
要么 11 个 MCP 全灭（`.mcp.json` 是清单文件名），要么 31 个 `.qoder-plugin` 插件全没了。

**根因**：前导点是"内部目录"约定没错，但**清单文件名**（`.mcp.json`）和
**插件清单所在目录**（`.qoder-plugin/`）也用前导点——一个字符级规则没法区分"名字"和"路径段"。

**修复**：只把"看起来像废弃"的有限词放进白名单（`_临时文件`/`归档`/`.old`/...），
不试图用通配规则。**白名单只列名、不做字符级语义**。
代价是会漏，但**不会误杀**。

**价值**：见过太多「过度泛化规则 + 修复误伤」循环。
把"绝不能误杀"立成硬约束，少走弯路。

## P20 — `quarantine_hit` 把"清单文件名"当目录判，11 个 MCP 全灭

**现象**：隔离函数 `quarantine_hit(rel, ...)` 拿 `rel` 整条相对路径的所有段判，
最后一段是 `.mcp.json`——它以点开头，被 `is_structural_debris` 命中。

**根因**：函数没把"文件名"和"目录段"分开。`Path::parent()` 之后只该看目录段。

**修复**：`let dir = rel.parent()?; for c in dir.components() {...}`
加 5 条回归测试覆盖 `.mcp.json` / `.claude-plugin` / `.qoder-plugin` / 嵌套普通词 / 隔离留痕位置。

**价值**：这种 bug 一旦进生产数据就难查。
单测的边际成本远低于生产数据修复成本。

---

## P21 — 「`legacy-` 任意深度匹配」杀掉真资产

**现象**：`architecture-visualization/skills/legacy-system-visualizer/SKILL.md`
被整片隔离——它的名字只是"可视化遗留系统"，是合法资产。

**根因**：「关键词能否作为判据，取决于它出现的位置（顶层 vs 嵌套）」，
不能用一个全局规则。

**修复**：拆成两个函数
- `is_structural_debris`（任意深度）：字符级规则（`_` / `.` / `.old`）
- `is_top_level_debris`（仅当 `depth == 1`）：命名（`backup` / `legacy-` / `obsolete`）

**价值**：「全局规则 + 深度例外」是处理命名多样性的标准模式。

## P22 — `cargo test` 子进程跑 11 分钟不动不报错

**现象**：`capabilitycore_desktop_lib-*` 测试进程 9.9 MB 内存、6.7s CPU、跑 11 分钟。
不是计算、不是 IO、不是编译——就是不动。

**根因推测**：selftest 端到端测试在 `current_exe().parent().parent()`
定位 `target/ac-selftest/`，在 Tauri 构建里相对路径计算与 `cargo test` 直跑不同。

**未定位到精确根因**。已采取的工程对策：
- selftest 改用 `CAPABILITYCORE_SELFTEST_DIR` 显式覆盖
- 再次遇到加 `RUST_LOG=debug` + strace 风格 ltrace

**教训**：cargo test 的死锁信号是「CPU 停 + 内存稳」，比 panic 难发现。
**立即杀掉**，不要等它自己结束。

## P23 — 506 个资产里"看起来空"的 1 个真空白 ≠ 5 个正则误报

**现象**：用"含 TODO/PLACEHOLDER/占位"正则扫出 5 条，肉眼全是误报。

| 资产 | 命中词 | 真实含义 |
|---|---|---|
| `data-normalizer` ×3 | "占位拒识" | 工具功能描述：会拒绝占位符 |
| `onboarding` ×2 | `[PLACEHOLDER]` | 它要查找的标记，非自己空 |

**根因**：正则没有"上下文"，字符串里出现就报。

**结论**：对"是否为空"必须**用判据定义**（本轮用"name+description 同时为空"），
不能用关键词扫描——后者在描述里"占位"是业务术语。

**价值**：本轮踩了 5 次正则误报后**才**改成结构化判据。
一开始就走结构化判定能省两次返工。

## S16 【高】M2 之前必须把"加白名单/隔离规则"路径固化

**本轮过程**：隔离规则改了 5 版（字符级 → 后缀 → 后缀+顶层 → 全文段名 → 字符+深度），
每版都引出新的误伤。每次都靠 4-5 条回归测试盖住。

**建议**：
- 隔离/跳过/限速这类"按命名空间行为"规则**集中放**到 `scan.rs` 顶部的常量数组里
- 每条规则**必须**有 1 条正向 + 1 条反向测试（"该隔离的"+"不该隔离的"）
- 文档里用一张表：规则名 / 适用深度 / 命中词 / 真实案例 / 误伤案例
- M2 加 tantivy 时，索引层的"分词跳过列表"也走同一套约定

**价值**：这种规则在 M2/M3 还会继续加（向量层、UI 层各有自己的"边界"）。
约定一旦定下来，加规则就变成"加一行 + 加两测试"，不会回到"改一次翻一次"。

## S17 【高】空壳判定要按"必填字段是否齐全"而不是"能力数是否为零"

**本轮踩过的两个坑**：
1. 用「能力数=0」当空壳判据 → 杀掉 19 个 `.claude-plugin` 真插件
2. 用「含 TODO/占位」正则判空 → 5 个误报，全是业务描述里出现的合法词

**正确判据（本轮已落）**：`name.trim().is_empty() && description.trim().is_empty()`
两个必填字段同时为空才是空壳。

**建议**：
- 把"空壳"判定函数上提到 `ac-core`，所有 kind 共享
- 在 M1.5 加"半空"判定（如 name 缺 description、version 不合规），
  但**降级为警告**而非隔离——半空可能是正在写的草稿

**价值**：判定"是否为空"是导入类产品的根本性命题。
判据错了，要么让用户怀疑产品坏了（误报），要么让垃圾污染检索（漏报）。

## S18 【中】在沙箱受限环境里跑 Rust 端到端测试的工程对策

**本轮问题**：M1 阶段发现 Rust 进程在 `C:\` / `D:\` 盘根等位置建目录被拒
（agent harness 镜像路径作用域沙箱），导致 Tauri GUI 进程无法启动、cargo test 路径计算可疑。

**建议**（M2 之前的工程动作）：
- 所有可执行文件的产物路径**显式锚在工作区内**（`target/` / `data/` / `ac-selftest/`）
- 端到端测试优先走"纯逻辑层 + 显式环境变量"模式（`CAPABILITYCORE_*_DIR` 三件套）
- **避免**默认用 `std::env::temp_dir()` —— 在受限环境里它会失败而且不报错
- CI 在"真实 Windows 桌面"环境跑一次 Tauri 启动，cargo test 在沙箱跑就够了

**价值**：让"开发环境"和"用户环境"在路径上一致是 Rust 桌面项目最被低估的工程债。

## S19 【中】用 `previous_result_diff` 留一个"上次 vs 这次"的变更审计

**本轮观察**：每次跑 `ingest_vendor` 都有"新增/更新/清除/未变化"统计，
用户能看到"哪 3 条被隔离清除了"。但**为什么**清除了，要去看跳过报告。

**建议**：
- 每次入库结果导出 `apps/desktop/public/diff.json`：
  `{ added: [...], updated: [...], removed: [...], quarantined: [...] }`
- 前端在"扫描完成"提示里点开就能看每条的 diff
- 把 `content_hash` 写入 diff，对"路径没变但内容变了"和"路径变了但内容没变"区分清楚

**价值**：导入类产品的"我刚才改了什么可见"是信任基础。
纯日志不可读，纯数字看不出问题，**结构化 diff** 是刚刚好。

## S20 【低】隔离/跳过理由前缀要稳定可解析

**本轮做法**：所有隔离跳过原因用 `"隔离目录（归档/临时/废弃）：{seg}"` 前缀。

**价值**：
- 后续 UI 解析扫描报告时，可以**只靠前缀分类**（"权限拒绝" / "隔离" / "解析失败"）
- 同一份报告既给用户看、又给工具看，不用维护两份

**建议**：
- 跨 crate 的"跳过原因"集中定义成 enum，序列化时统一前缀
- M2 加 CLI 标志 `--show-skipped-by=隔离` 时直接做 prefix 过滤

**价值**：用统一前缀做"自然分类"是日志/报告设计的便宜方案。
比每个 tool 各自造 JSON 字段稳定得多。

## S14 【中】Tauri IPC 路径需要真正的运行时验证手段

**M1 遗留**：当前执行环境里 GUI 进程起不来，
`capabilitycore-desktop.exe` 的 IPC 链路**只验证到编译与类型层面**，
没有跑过真实进程。

**风险**：命令签名对了不代表序列化对了。
`invoke` 的参数命名（Rust `snake_case` ↔ JS `camelCase`）、
`Result<T,String>` 的错误回传、Tuple 返回值（`[IngestSummary, RegistryStats]`）
的解构，这些只有真跑起来才会暴露。

**建议**（M2 开工前做）：
1. 在 CI 或本地加一条 **IPC 契约测试**：不经过 WebView，直接调用命令函数本身
2. 或者提供一个 `--selftest` 命令行开关：`capabilitycore-desktop.exe --selftest` 依次调一遍
   所有命令并打印结果，不开窗口
3. Tauri 应用本体另配一条**冒烟测试**：启动 → 等待 → 截图 → 退出

**理由**：M2/M3 的命令会越来越多，缺一个能自动跑的验证通道，
每加一个命令都要靠"手动点一下看看对不对"。

## S15 【低】预览快照机制值得保留并制度化

**M1 做法**：`ingest_vendor` 例程额外导出 `apps/desktop/public/preview.json`
（真实数据的 JSON 快照，含完整 manifest），浏览器预览模式直接 fetch 它。

**价值**：
- 改界面时不必每次重编 Rust，迭代快一个数量级
- 可以在**没有真实资产的机器**上（CI、别人的电脑）看真实排版
- 顺带成了一个"数据体检"工具——本轮多个 bug 就是在分析这个 JSON 时发现的

**建议**：
- 把它写进开发流程文档，作为 M1 之后的标准动作
- 快照文件**不要**进版本库（984 KB 且每次入库都变），加 `.gitignore`
- 未来可以扩展成"导出某次快照"，用于回归对比
