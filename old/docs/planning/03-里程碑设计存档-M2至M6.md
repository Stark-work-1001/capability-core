### M3 混合检索

**目标**：把召回率提上去，同时不让 LLM 成为瓶颈。

| 问题 | 答案 |
|---|---|
| (a) 完成标志 | 构建 100 条标注查询基准集，命中率 ≥ 目标阈值；**人为断开向量服务，查询仍返回结果且降级日志明确** |
| (b) 功能链路 | ① 全文召回 ∥ ② 向量召回 → ③ RRF 融合排序 → 置信度评估 → 低于阈值则 ④ LLM 判定消歧 |
| (c) 需开发的功能 | MiniLM 嵌入服务（ONNX，Rust 端推理）/ 向量存储（内存 HNSW 或 sqlite-vec）/ RRF 融合器 / 置信度评估器 / 健康检查与熔断 |

**关键约束**：LLM 判定**不是默认路径**，只在低置信时触发。依据 NeMo 数据（+8.7 分 = 160 倍延迟）。

### M5 多智能体协同

**目标**：N 个智能体通过一个 MCP 端点并发调用共享工具池。

| 问题 | 答案 |
|---|---|
| (a) 完成标志 | 3 个以上智能体并发调用同一工具池无冲突；每个智能体看到的能力集按其身份维度裁剪；完整调用链可追溯 |
| (b) 功能链路 | 智能体注册（含身份维度）→ MCP 会话建立 → 委派链构建 → 能力裁剪投影 → 并发调用 → 审计落库 |
| (c) 需开发的功能 | MCP server 实现 / 智能体注册表 / `admits()` 权限裁剪 / 委派链管理（含环检测）/ 并发工具池（引用计数与排队）/ 审计日志 |

**需求 8 的答案（多智能体共用工具）**：
在 `ac-mcp` 中实现**能力投影**——每个智能体连接时，依据其 `CapabilityIdentity`
通过 `admits()` 过滤出一个工具子集，工具池本身共享但视图独立。
共享资源（如浏览器实例、数据库连接）用**租约 + 引用计数**协调，避免独占。

**⚠️ 给 M5 实现者的一条硬约束（复核记录，勿重新发明）**：
`ac-mcp` 接入检索时，应当是
`pub use ac_retrieval::searcher::Searcher;`
——**复用并转出 `ac-retrieval` 已经定义好的 `Searcher` trait**，
**不要**在 `ac-mcp` 里另写一份面向消费者的 consumer trait。

理由：本切片已经为了避开循环依赖，把 `Searcher` 定义在了 `ac-retrieval`
（见「本轮与设计文档的偏差」第 1 条；当时 `ac-mcp` 还是 14 行空壳，没有可动的东西，
复核也确认现在**不必**回头改）。等 `ac-mcp` 真正建起来、并且需要一个
「面向调用方的窄接口」时，正确做法是**新 trait 只做委派**：
`impl` 它并转调 `RetrievalSearcher`，而不是复制一份同名同签名的 trait。
两份独立演化的 trait 迟早会漂移，而漂移的代价是「编译通过但检索行为不一致」——
这类 bug 极难排查。等真的需要时，请在 `ac-retrieval/src/searcher.rs` 的模块注释里
补上这条演化的理由。

##### 依赖方向：谁定义 trait

耦合点清单写「registry → retrieval，`AssetStore`，retrieval 定义、registry 实现」，
同表的箭头表示 **ac-registry 依赖 ac-retrieval**。于是本轮的实际方向是：

```text
ac-retrieval  ──定义──▶  AssetStore
ac-registry   ──实现──▶  AssetStore
（ac-registry 的 Cargo.toml 里出现 ac-retrieval；反过来没有）
```

因此 `AssetFilter` / `AssetRow` 必须活在 ac-retrieval 里，**不能**复用
`ac_registry::AssetSummary` —— 后者是 UI 列表形状，让它出现在 trait 签名里
等于把实现方拖成定义方的必要依赖，方向又反过来了。
`cargo tree -p ac-retrieval` 实测依赖只有 ac-core / serde / serde_json / tracing。

##### 降级机制（本切片最实质的产出）

M2 最难的一条完成标志是「**在向量库和 LLM 全部不可用时仍能返回结果**」。
这轮把它做成了**类型层面的性质**，而不是一条靠自觉维持的纪律：

| 机制 | 落点 | 作用 |
|---|---|---|
| `Searcher::search` 返回 `SearchResult` 而**不是 `Result<_, E>`** | `searcher.rs` | 没有可冒泡的错误通道，「仍能返回」在类型上就是必然的 |
| `Stage::Structured` 是唯一非可选阶段 | `health.rs` | 查询能否成功**只看**基线，其余全是可选层 |
| `StageState` 四态：`Absent` / `Disabled` / `Failed` / `Ready` | `health.rs` | 「没这能力」与「有这能力但挂了」必须可区分——前者无需处理，后者要告警熔断。合成一个 bool 就丢了信息 |
| 未声明的阶段按 `Absent` 处理 | `health.rs` | 没被显式声明成可用，就**不得**被当成可用（漏声明是最危险的默认值） |
| 每次查询必带 `DegradationReport` | `pipeline.rs` | 满足 M3 完成标志里的「降级日志明确」：上层永远能回答「这次为什么只有这些结果」 |
| 可选层跑在基线**之后**的 `augment` 里 | `pipeline.rs` | 任何一路出错只能就地降级，冒泡不到查询层 |

**实测（真实 `data/registry.db`，506 条）**：

```text
健康快照: structured=ready full_text=absent vector=failed(向量库不可用) llm=failed(LLM 不可用)
查询 kind=skill -> 命中 460 条
降级报告: used=structured skipped=full_text(absent),vector(failed(向量库不可用)),llm(failed(LLM 不可用))
```

##### 本轮与设计文档的偏差（3 处，均附理由）

1. **`Searcher` trait 定义在 ac-retrieval，不在 ac-mcp。**
   设计写「mcp 定义 trait，retrieval 实现」，但同一张表的箭头 `mcp → retrieval`
   意味着 ac-mcp 依赖 ac-retrieval；若 ac-retrieval 去实现一个定义在 ac-mcp 里的
   trait，就必须反向依赖 ac-mcp，与该箭头相反并**直接构成循环依赖**（硬性约束 #4）。
   唯一无环的读法就是现在这样：retrieval 定义自洽的 `Searcher` 并提供
   `RetrievalSearcher` 实现；将来 ac-mcp 建好时由它定义面向消费者的 trait，
   再委派给 `RetrievalSearcher`（它本就依赖 ac-retrieval）。
2. **新增 `Registry::tags_of_asset()`。** 唯一一条新 SQL。原因：
   `AssetSummary` 是 UI 列表形状、不带标签，而 `AssetRow` 需要标签用于结果回显
   与将来向量匹配。它用与 `all_tags` **完全相同**的 `json_each` 展开，
   保证「回显的标签」与「能被筛中的标签」出自同一条路径。
3. **`Registry.conn` 从私有放宽到 `pub(crate)`。** 让同 crate 的
   `retrieval_impl` 能取标签。仍是 crate 内部可见，不扩大对外 API。

**④ store 级失败被静默吞成「成功的空结果」（真缺陷，已修）。**
`retrieval_impl.rs` 原写 `self.query_assets(&aq).unwrap_or_default()`：
库被锁住 / 损坏 / 缺失 → 返回**空列表且无任何错误** → 流水线报
`used=[structured]`，即**对外宣称结构化基线跑通了、只是没匹配到东西**。
对一个核心承诺是「永远返回结果」的检索层，这是最坏的失败模式：谎报成功。
当时的测试基础设施也**看不见**它——`InMemoryStore::unhealthy()` 只把 `is_healthy()`
翻成 false 却照样返回行，于是「库坏了」与「库里没有」在测试里长得一模一样。

修法（详见 `ac-retrieval/src/store.rs` 与 `pipeline.rs` 的文档注释）：

1. `AssetStore` 增加 `try_query() -> Result<Vec<AssetRow>, String>`（默认实现包 `query()`，
   **任何会失败的后端必须覆写**）；`query()` 降级为**有损视图**并如实标注。
2. 流水线走 `try_query()`，失败记成 `Stage::Structured = Failed`——
   **错误不冒泡**（`Searcher::search` 仍无 `Result`）与**状态不说谎**同时成立。
3. `is_healthy()` 被真正接进流水线：只在**失败分支**问，用来区分
   「存储自认已不可用」与「查询单独失败」，两者处置不同。happy path 不问——
   它没有信息增益却要多付一次全表 `COUNT(*)`，与「P95 < 50ms」冲突；
   而 `try_query` 返回 `Ok` 时基线就是交付了，这比任何预检查都强。
4. `InMemoryStore::unhealthy()` 改成**真的拒绝**（`Err`），并故意保留 `rows`——
   锁住的 SQLite 库里是有数据的，只是读不出来。
5. `DegradationReport` 增加 `baseline_state()` / `baseline_failed()`，
   「真的没有匹配」与「基线根本没跑成」从此可区分。

##### D5：词表数字与它的过滤口径（两个数不可混用）

上表第一行 **7,795** 与第二行 **19,765** 过去在文档里被混用过一次，是错的。
它们是两个不同函数的输出，**过滤器不同**，不可直接比较：

| 数字 | 出处 | 过滤器 |
|---|---|---|
| **7,795** | `mine_vocabulary()` —— **用来 BUILD 语料的词表** | `t.chars().count() >= 2` |
| 19,765 | `profile(&rows, Some(2))` —— 建完之后统计语料 | 同为 `chars >= 2`，与上一行同口径 |
| 19,988 | `profile(&rows, None)` —— 仅供参照 | 不过滤（`analyze_terms` 原始输出口径） |

**引用时必须带上过滤器**：`去重词表 7,795（chars>=2）` 是合法的；
写成「去重 token 19,988」却不说明它用的是不过滤口径，则与建语料所用词表无关。
旧文档里的 **19,032** 无法对应到当前任何一个函数输出——它既不是 `mine_vocabulary`
的返回值，也与 `profile` 的两个口径都不符，属于历史误记，已作废。
`m2_perf_real` 现在运行时会把三个数连同各自口径一起打印（见
`artifacts/m2final-latency-m2perfreal.txt` 第 [0]/[1] 节），不再依赖人工转述。

**诚实备注（不要跳过这一段）**：真实词表语料的 P95 也达标，
但它的查询集与语料**同源**（查询全部取自高频真实词），而这类词在每篇里都出现，
因此 BM25 分数天然被拉平 —— top1–top20 分差的 `min` 只有 1.0% 就是这个现象的直接体现。
**「不同分个数更高」不等于「排序更好」**：该指标只说明分数没退化成常数，
不说明**正确的文档排在正确的位置**。要真正判定排序质量，
必须有一个带标注的查询集（ground truth）算 NDCG/MRR —— 那是 M3 的
「100 条标注查询基准集」的范围，本切片**没有做，也不假装做了**。

**结论范围（必须与上表一起被引用，不得单独摘出延迟数字）**：

| 语料 | 两条延迟判据 | 能否支持相关性 / 排序质量结论 |
|---|---|---|
| 合成语料（`m2_perf`） | **双双达标**（0.514 s / 6.00 ms） | **不能** —— 11,175 去重 token、18 个 token 每篇必现、top1–top20 分差 2.3–5.2%，排序近乎退化 |
| 真实词表语料（`m2_perf_real`） | **双双达标**（0.288 s / 2.76 ms） | **仍然不能** —— 它只让词表多样性与分数区分度**可被量化**，不等于相关性被证明 |

即：**排序质量（relevance / ranking quality）目前仍是 UNPROVEN。**
两套语料通过的是同一件事——**延迟**。任何把上表延迟数字读成
「检索质量已达标」的说法都是越界；要闭合这个缺口，需要带标注的查询集
算 NDCG/MRR，属 M3 范围。

#### 关于「不要碰用户的 registry.db」（M2 事故后的硬纪律）

本切片曾把用户的 `data/registry.db` 打开成「字节不同、内容完好」——
`Registry::open` 会建表/迁移并**重写 SQLite 页**，打开本身就是写操作。
此后确立并**已用测试强制**的纪律：

1. 要在真实数据上验证，先 `std::fs::copy`，只打开**副本**；
2. 要证明「原库没被动过」，用 `std::fs::read` 算 SHA256 —— 那是读文件字节，
   **不经过 SQLite**；
3. 无参运行任何 example 都不得写任何东西；
4. `ingest_vendor`（唯一正当写库的建库工具）必须显式传入**绝对路径**，
   无参只打印计划并退出。

守门测试：`db_safety_guard.rs`（ac-registry）。它**运行时**读 `examples/`，
而不是用 `include_str!` —— 后者实测抓不到任何东西：cargo 不会因为
`examples/` 下文件变化而重编 lib 目标，于是测试读到编译期嵌进去的旧内容，
在事故版本下依然全绿，属于比没有守门更糟的假信号。
守门本身另有一条自检（`the_guard_actually_rejects_the_original_incident`），
用事故版本的原始写法做样本，要求它被判红 —— 避免「规则写错导致恒真」。
实测：事故版本 → 退出码 101 并指名 `m2_e2e.rs`；修复版本 → 0。

#### D1–D6：评审复查轮（2026-10-16 23:00–23:40）

上一轮的「绿灯」里有 **6 处判定缺陷**。它们有一个共同点：**每一处都能产出"达标"，

##### D1：守门的"反证规则"漏掉了被 rustfmt 折行的 let 绑定（警示案例）

**真实缺陷不是"规则写错了"，是 `binding_def` 只读了 let 绑定的**第一物理行**。**
一个 32 KB 的守门测试，在三种**日常写法**面前是全盲的：

```rust
// ① 被折行的路径链 —— rustfmt 对长路径必然这么折
let src = read_example(
    "ingest_vendor.rs",
);

// ② 括号不平衡 / 缺终止符
let mut db = PathBuf::from(
    db_arg

// ③ 下一行以 '.' 开头
let out = pack_root()
    .join("apps")
```

①②③ 都不是刁难人的边角写法，**① 尤其常见**：任何超过 ~40 字符的路径链，
`rustfmt` 都会把它折行。于是一条**只认单行**的规则，在真实代码里的实际覆盖面远低于
它给人的安全感 —— 守门文件 32 KB、规则写得极认真，但依然漏。

**修法**：`binding_def` 改为**消费续行** —— 在括号不平衡、缺终止符、
或下一行以 `.` 开头时继续往下读，把完整的绑定拼回一行再判。返回值从
裸字符串改成 `Option<String>`（读不成就是"不是可判定的 let 绑定"，**不判红也不放过**）。
代价是一次 IO，收益是守门重新覆盖真实代码形态。

**可证伪证据**（不是"我认为它修好了"，是三个样本必须变红）：

| 样本 | 形态 | 结果 |
|---|---|---|
| `bypass_live_var.rs` | 变量改名绕过（评审实证的原始事故形态） | **红** |
| `bypass_helper_fn.rs` | 绕经辅助函数间接拿到库路径 | **红** |
| `bypass_join_chain.rs` | 被折行的 `.join()` 路径链 | **红** |

三者在修复前**全部绿**（`kernel/target/_falsify.txt`：守门对
`bypass_live_var.rs` "竟然通过了规则 2"），修复后全部红。
外加守门自检 `the_guard_actually_rejects_the_original_incident` 也保持红 ——
**守门本身仍然能拒绝事故版本**，没有被改坏成恒真。

> **留给后人的一句话**：`守门测试写得再大，不等于它在判你以为它在判的东西。`
> 写守门的第一问不是"规则完备吗"，而是"**它在真实代码形态上覆盖多少**"。
> 判断办法只有一个：**拿几份真实的、会被 rustfmt 折行的代码去试它，试到红为止。**

##### D2 / D3：建索与延迟的"假绿"（附可证伪证据）

**D3 的缺陷**：建索成功与建索快慢是两件事，旧判定**只看耗时**。
而 `FullTextIndex::attach` **永不返回 `Err`**（设计如此），失败全部落进 `state()`。
于是**一次完全失败的建索会非常快**（它什么都没做），旧代码把这个"极快"
当成"性能极好"报出达标 —— **索引文档数 0，同时写着"达标"。**

**AFTER 实测（本次亲跑，两套基准都是索引层失败）**：

| 基准 | 强制方式 | 状态 | 文档数 | 耗时 | 判定 |
|---|---|---|---|---|---|
| `m2_perf` | 默认 `%TEMP%\capabilitycore-m2-perf-index` 不可写（拒绝访问） | `failed(索引重建失败（无法创建目录）…)` | **0** | 0.026 s | **未达标**（建索未完成） |
| `m2_perf` | 指定目录加拒绝 ACL | `failed(索引重建失败（无法清除旧索引）…)` | **0** | 0.026 s | **未达标** |
| `m2_perf_real` | 索引目录加拒绝 ACL | `failed(索引重建失败（无法清除旧索引）…)` | **0** | 0.016 s | **未达标** |

日志：`artifacts/m2final-d3-m2perf-tempdir-denied.txt`、
`m2final-d3-m2perf-acl-denied.txt`、`m2final-d3-m2perfreal-acl-denied.txt`。
与 BEFORE（`kernel/target/_synth_rerun.txt`，`
判定: 0.031 s < 10.0 s -> 达标` **且 索引文档数: 0**）逐行对照，同一场景、

##### 第三个同族假绿面：P95 是否只统计"成功查询"？

**已修，且这是本轮修得最关键的一处 —— 因为它比 D3 更隐蔽。**

问题：某次查询若因全文层 `Failed` 而退化成"只走结构化基线"，
它**不会变慢**（索引层压根没参与，省掉了 BM25 与精排），
反而会**更快**。如果把它算进 P95 样本池，**索引死掉的场景下 P95 会变得更漂亮** ——
**这是把故障平均掉的误导方向**，与 D3 同族。

修法（三步，缺一不可）：

1. **退化查询不进样本池**：`skipped_stage(Stage::FullText)` 或
   `baseline_failed()` 为真的样本被 `continue` 跳过，**不被当作一个正常样本**；
2. **强制计数呈现**：单列一行 `降级查询: N 个（已从 P95 样本池中排除）`，
   附最多 5 条样例（含 `degradation.summary()` 的完整归因）——
   **不是静默丢弃，是显式呈现**；
3. **退化过半时拒绝报数**：`degraded * 10 > queries.len()` 直接 `panic!`，
   因为此时 `samples` 已空、任何延迟数字都不再支撑任何结论。

**实测**：在索引层失败场景下，`m2_perf_real` 打印
`降级查询: 500 个` 后**退出码 101**，panic 文本：
`查询集中有 500/500 次查询发生降级：P95 量的是一个已经掉了的索引的耗时，不能报数。`
（`artifacts/m2final-p95-degradation-full.txt`）。
健康场景下两套基准均为 `降级查询: 0 个`。**这条已修，不需要再处理。**

##### D4：`ingest_vendor` 的两个 `preview.json` 覆盖 —— 已纳入同一道门

`ingest_vendor` 除写库外还会覆盖 `apps/desktop/public/preview.json` 与
`apps/desktop/dist/preview.json`。它们**不是数据库**，所以
`Registry::open` 那条红线**根本看不到它们** —— 这正是它们必须另行声明的原因。

**决定：不做豁免，走同一条"显式授权门"。** 理由：豁免等于承认"存在一类
静默覆盖没人负责"，而这两个文件被覆盖的后果正是 UI 显示的资产数与数据库不一致 ——
**用户会看到错的数字，且没有任何告警**。这种后果不该被归类为"无需保护"。

落地（两处，均已生效）：

- `ingest_vendor.rs` 主流程在任何写入**之前**明写两个目标路径
  （`会被覆盖 : apps/desktop/public/preview.json` / `…dist/preview.json`），
  无参分支仍只打印计划并退出；
- `db_safety_guard.rs` 的 `guard_ingest_vendor_announces_every_path_it_overwrites`
  **机械校验**这一点：`preview.json` 的声明数必须 `>= 2`，且无参分支必须仍然存在。
  以后新增**第三个**覆盖路径时，它同样会被要求报出来。

实测：本轮 `cargo test` 中该测试 `... ok`（日志
`artifacts/m2final-test-regression.txt`）。

##### D5 / D6：口径与语料分布（见上文两处小节）

- **D5**：词表数字必须与它的过滤器一起引用，见上文「D5：词表数字与它的过滤口径」。
  旧文档的 **19,032** 无法对应任何函数输出，已作废；
  正确成对是 **7,995**（建语料口径 `chars>=2`）与 **19,765**（同口径统计）。
- **D6**：`m2_perf_real` 不再把每篇都补/截到恰好 681 字符 —— 真实库的

  而那正是排序区分度的来源。实测每篇字符数已回到 `mean 886.3 / min 101 / max 4167`。
