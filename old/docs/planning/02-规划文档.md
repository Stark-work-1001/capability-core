### 本轮修掉的三个真根因（勿重复踩）

1. **启动崩溃 `0xC0000139` / TaskDialogIndirect** —— exe 需嵌 Common-Controls v6 manifest 才会激活 `comctl32.dll` 的 `TaskDialogIndirect` 符号。已在 `build.rs` 用链接器开关 `/MANIFEST:EMBED` + `/MANIFESTINPUT:` **成对**给出（只给 INPUT 会 LNK1220）。**不再需要**手动跑 `embed-manifest.ps1`。
2. **exe 窗口正常但内容是错误页 `ERR_CONNECTION_REFUSED`** —— 根因不是「没起 dev server」，而是裸 `cargo build --release` 出的 exe 是**永久 dev 模式**：`dev = cfg!(not(feature="custom-protocol"))`，而该 feature 只有 `tauri build` 会开，于是 tauri-codegen 跳过 `frontendDist` 资源嵌入、转连 `devUrl`。**修法**：`Cargo.toml` 加 `default = ["custom-protocol"]`。
3. **`ops::rescan()` 死锁** —— 持有 `st.registry` 锁的同时调用 `stats_of()`，后者对同一个非重入 `std::sync::Mutex` 二次加锁，同线程必死。表现为全量 selftest 挂死 589s、CPU 冻结、0 字节输出。**修法**：把 `IngestSummary` 的计算放进独立作用域，让 guard 先释放，再在锁外调 `stats_of()`。

> 上述死锁曾是「自检 13/13 全过」的重大隐患：快模式在 rescan 之前就返回，根本走不到那段代码，所以**旧的全绿结果属于巧合通过**。现已由全量（非快模式）自检真正覆盖。

### 改名的最高风险点（务必知道）

`build.rs` 通过 `/MANIFEST:EMBED` + `/MANIFESTINPUT:` 在**链接期**把 Common-Controls manifest 嵌进 exe。改名时如果 manifest 文件名改了而 `build.rs` 里的路径没同步：

```rust
if !manifest.is_file() {
    println!("cargo:warning=manifest not found ...; skipping embed");
    return;                          // ← 只警告，不报错
}
```

结果是 **编译成功、exe 生成、启动即崩 `0xC0000139`**。改名当天就撞上了 `LNK1327: 运行 mt.exe 期间出错`——因为 manifest 被改坏成了非法 XML。

**改名后第一件事**：验证 exe 里确实带上了 manifest，不要只信构建退出码。

```powershell
$b=[IO.File]::ReadAllBytes('target\release\assets-desktop.exe')
$s=[Text.Encoding]::ASCII.GetString($b)
$i=$s.IndexOf('assemblyIdentity')
$i -ge 0 -and $s.Substring($i,500) -match 'Microsoft\.Windows\.Common-Controls'
```

> `mt.exe` 在本机不可靠（返回 c1010070），且 manifest 以 UTF-8 存储——用 UTF-16LE 字节搜索会返回 -1 并误判为「manifest 丢失」。上面这个 ASCII 字节搜索是实测可用的方法。

### ⚠️ 改名当天踩到的坑：脚本式改源码会静默毁文件

改名时用 PowerShell 的 `-replace` 和 `[IO.File]::ReadAllText()` + `WriteAllText()` 批量改源码，造成了**静默损坏**：

```
健康 → heglth     encoding → encoeing     Windows → Wineows
main  → mgin       standalone → stanealone  amd64 → ame64
```

即**每个字母 `d` 都被吃掉**。编译报 `cannot find attribute cfg_gttr` 才发现。manifest 因为同样原因变成非法 XML，直接导致 `LNK1327`。

**正确做法**：

- 改源码用带 fs 观察策略的编辑工具做**精确替换**，不要写脚本做 read-modify-write；
- 需要批量恢复时用 **`robocopy`**（二进制安全，绕开编码问题）从可信源重取，**不要用字符串 API 写回**；
- 每次批量改完**立刻编译**，不要等到最后 —— 损坏是静默的。

> 这是本项目第三次栽在「用工具改源码」这个动作本身（此前有一次 `store.rs` 被截断 2715→1207 行）。所有子智能体的任务书里都写着这条纪律，结果协调者自己违反了。

### 2. `维修站` 侧栏

用户要求：故障类型 / 故障内容 / **能否自维修** / **是否需要求援主对话模型**。

- `Stage` / `StageState` / `DegradationReport` 已能区分「结构化失败 / 全文层失败 / 向量层失败 / LLM 失败」，并区分「缺席 Absent / 禁用 Disabled / 故障 Failed / 就绪 Ready」四态；

**风险提示**：「自维修」若指**自动修改用户的插件文件**，风险极高且不可逆。
建议实现为 **「诊断 → 生成修复建议 → 用户确认 → 应用」**，而不是无人值守自动改文件。

### 3. `模型接入` 侧栏

用户要求：能力核心自带算法（检索、修复）驱动；先建多协议支持；协议测试不通过时，再用云端或本地模型驱动故障解决。

### 功能说明的两种方式

用户给出的两条通路：
1. **从能力核心数据库直接拉取**（已实现：`list_assets` / `get_asset` / 结构化过滤 / BM25）

## ✅ M3 交付：对外接口 + 多智能体路由协调（2026-10-17 落地）

上一节把主线定成「对外能用 + 多路不打架」。本轮把这两件都实现了，
落在一个新 crate **`ac-mcp`**（此前是空壳，只有 `CRATE_NAME` 与一个占位测试）。

### 一、对外接口：两种形态，一套内核

两个形态**共用 `gateway::CapabilityGateway`**，传输层只做协议解析、不含业务判断。
这是刻意的：两条链路各写一份查询逻辑，就会在某次改动后给出不同答案，
而「同一个问题两个接口答案不一样」是最难排查的一类故障。

| 形态 | 协议 | 为什么选它 |
|---|---|---|
| **MCP server** | JSON-RPC 2.0 over **stdio** | MCP 的标准接入方式。不占端口（18181/18182 的硬约束对它天然免疫）、天然单租户、主流软件默认走这条 |
| **HTTP API** | HTTP/1.1 + JSON，**仅 GET** | 给不方便拉子进程的调用方（脚本、其它语言、监控）。版本前缀 `/api/v1` |

对外暴露的能力共四类，**全部只读**：
`search_capabilities` / `get_capability` / `list_tags` / `health`。

#### HTTP 路由表

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/healthz` | 存活探针，永远 200（只说明进程活着）|
| GET | `/api/v1/version` | 版本信息（api / crate_version / schema_version / parser_rev）|
| GET | `/api/v1/health` | **就绪**探针，注册表故障时返回 503 |
| GET | `/api/v1/capabilities` | 检索：`q` / `kind` / `tag` / `min_authority` / `limit` / `offset` |
| GET | `/api/v1/capabilities/:id` | 单个能力详情 |
| GET | `/api/v1/tags` | 标签清单（按调用方可见范围重算计数）|
| GET | `/api/v1/agents` | 已注册智能体（协调状态可见）|

**非 GET 一律 405**。路由器里根本没有注册任何写动词——
所以「某个写接口忘了加鉴权」在结构上就不可能发生，而不只是靠约定。
`guard_gateway_exposes_no_asset_mutation` 另有一条源码级守门：
`gateway.rs` 里出现 `UPDATE assets` 一类语句即编译期测试失败。

#### 一条刻意的设计：不可见资产返回 404 而不是 403

用 403 区分「存在但无权」，外部智能体就能靠遍历 id 把整个库的存在性摸出来——
裁剪等于没做。所以 `service::detail` 对被裁掉的资产返回 `NotFound`，
与「真的不存在」完全同形。`service::tags` 同理：标签计数只统计**可见资产**上的，
否则「某个标签只存在于高权限资产上」本身就是一条侧信道。

### 二、多智能体协调：裁剪 / 分配 / 冲突 / 审计

#### 2.1 能力裁剪（三层，从松到紧）

| 层 | 判据 | 拒绝原因码 |
|---|---|---|
| 1 身份 | `CallerIdentity::admits(asset_identity)` | `identity_insufficient` |
| 2 授权 | `Visibility.allow` 白名单 | `not_granted` |
| 3 公开性 | `Visibility.deny` 黑名单 | `denied_by_policy` |

顺序不能换：先看身份再看白名单，才能保证「身份不够」不会被记成「没授权」——
这两件事的处置完全不同（前者是配置错了，后者是正常收窄）。

##### ⚠ 本轮改动过一处既有语义：`dimensions` 从「必须逐条覆盖」改为「声明才收窄」

`ac_core::CapabilityIdentity::admits` 的 dimension 规则是
「目标的每个 dimension 都必须被调用方逐条覆盖」。**那是为委派链设计的**
（上级要精确声明下级用的每个维度）。

但对外接口是**检索**，不是委派。实测：库里 506 条资产**每一条**都带
`dimensions={cost_tier, domain}`，而一个「只想找只读技能」的调用方根本没声明 domain。
沿用委派规则的结果是**一条都看不到**——实测 `anonymous` 在 460 条 skill 里 visible=0。

所以 `CallerIdentity::admits` 把 dimensions 定性为**调用方主动施加的收窄条件**：
声明了 `domain=geo` 就只准看 geo 的，一个都不声明就不按维度收窄。
**安全三维（authority / side_effect / tool_posture）一律不放宽**——
那三维才是「动得了」的真判据，由 `safety_dimensions_match_ac_core_admits_exactly`
对拍防漂移；`undeclared_dimensions_do_not_hide_assets` 正面锁定这条例外。

##### 匿名调用方的默认档位：Observe（不是 Read）

匿名 = `Authority::Observe + SideEffect::None`。选 Observe 而非 Read 的理由是
**默认档位要选「能让接口可用」的那一个**：infer 把没有明确读写声明的资产归为 Observe，
按 Read 收窄会让接口在真实库里几乎什么都看不到——「安全但没用」不是好默认。
它依然安全，因为本接口只读：放大的是「看得见」，不是「动得了」，
而 `side_effect` 仍是 `None`，对外更没有任何写路由。

#### 2.2 路由分配

| 维度 | 选择 | 理由 |
|---|---|---|
| 并发上限 | 每个智能体可配 `max_concurrent`（默认 1）| 默认互斥是最保守的可用形态 |
| 排队 | 有界 FIFO，超 `MAX_QUEUE=32` 即拒 | 无限队列会把「慢」变成「挂死」 |
| 争用同一能力 | **允许并发读**（Shared），按各自身份裁剪 | 只读语义下争用无副作用 |
| 互斥模式 | Exclusive：他人持锁则排队 | 为将来的写接口预留，语义已就位且有测试 |
| 超时 | `LEASE_TTL_MS=60s`，`reap()` 回收 | 持有者崩溃是常态；无超时必然死锁 |

**释放即交接**：`release()` 会把队首**提升**为持有者，而不是让队首留在队列里
等自己再发一次请求——那样一旦它下次请求撞上队满，就永远拿不到，排队毫无意义。
回归测试 `release_promotes_queue_head_instead_of_orphan_it`。

租约**只在内存**：重启后归零。这是刻意的——租约是「现在谁在用」的瞬时事实，
持久化一份过期租约比丢失它更危险。需要长期事实的走 `agent_capability_usage`。

#### 2.3 冲突处理

本轮接口只读，所以两个智能体抢同一份**可变**资源在本轮不会发生。
但协调机制现在就立住了，理由有二：接入是无序的（谁先拿到使用权必须由中枢说了算），
以及租约语义已经在库里、已有测试覆盖，而不是和真正的写路径一起第一次被调试。

#### 2.4 调用审计

落库目标固定是 M2.5 已有的 `agent_capability_usage`，`source='mcp'`。
审计写在 `service` 层而非传输层——因为「谁」来自协议解析出来的 `Caller`，
写在传输层就要写两遍，两份审计实现迟早漏记一类调用。

##### ⚠ 本轮修掉一个真实缺陷：审计失败曾被 `unwrap_or(0)` 吞掉

初版 `acquire_and_audit` 里审计失败只记 `call_count=0` 然后照常返回成功。
后果：**未注册智能体也能「成功」调用并占住路由位**，
调用方拿到一个看不出异常的响应。这与 M2.5 已定的契约
（「未注册一律报错，绝不顺手建一行 agents」）直接冲突。

现在的顺序是「**先落审计再分配**」，失败**直接冒泡**：
审计是这次调用的准入凭证；顺序反过来时，未注册智能体会先拿到内存租约、
再在写库时失败，于是「没被授权」却短暂占住了路由。
回归测试 `acquire_and_audit_rejects_unregistered_agent_instead_of_swallowing`。

### 三、常驻与自检

`/healthz`（存活）与 `/api/v1/health`（就绪）**刻意分开**：
注册表故障时就绪探针返回 503，否则监控会一直显示健康。
依赖状态逐阶段如实上报——结构化基线 `ready`，全文层 `absent`（本轮未挂索引），
向量层 `absent`。**缺席要说出来**：一个阶段没被提到，与被明说「缺席」，
对排查是两种体验。

### 四、端口与隔离（遵守既有硬约束）

- 本项目 HTTP 用 **18195**；**18181/18182 属 memora，全程未触碰**。
- MCP 走 stdio，**根本不占端口**，所以这条链路天然不可能与 memora 撞车。
- 端口可用性**用实际连接探测**（`TcpClient.BeginConnect`），不只看 `ss -tlnp`。
- 未复用 memora 的 venv，未安装任何东西。
- 调试时曾把 `assets-serve.exe` 指向 `%TEMP%`，SQLite 报
`unable to open database file`（短路径 + WAL 不可用）；改为工作区内副本即正常。
测试**一律用副本**，`data/registry.db` 的 sha256 全程未变。

- **HTTP 侧的身份传递**：`route()` 目前固定用匿名调用方；

- **A 让 11 个 MCP server 变成真正可调用的工具**，这是「能力核心」最核心的价值。
- C 依赖宿主，先只做信息展示。

## 🔧 维修架构：中枢负责「定位」，智能体负责「维修」（2026-10-17 用户定）

### 职责分离（关键设计）

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **中枢** | **汇报 + 定位**故障：什么坏了、坏在哪个具体位置、为什么坏、修复需要什么前提 | **不猜怎么修** |
| **接入的智能体** | 拿到定位信息后**执行维修**，用其模型能力判断与操作 | 不负责发现故障 |
| **中枢（纳管）** | 智能体修好后，把能力实体存进中枢自己的范围 | |

这个分工避免了中枢去猜 `${QODER_NODE_RUNTIME}` 是什么这类不可知问题——**中枢只报告「这里有个未展开的环境变量 QODER_NODE_RUNTIME」，由智能体决定填什么。**

### 存储结构（已采纳）

```
capability-core\
  data\registry.db         ← 数据库：元数据 / 状态 / 故障记录 / 修复历史
  assets\                  ← 分散文件夹：纳管的能力实体
    mcp\<id>\               ← 修好的 MCP server + 启动脚本 + 依赖
    skill\<id>\             ← 纳管的技能副本
```

**为什么要两套存储**：数据库适合查询与状态机（哪些坏了、修过几次、当前能否用）；文件夹适合放**能直接执行的东西**（脚本、二进制、配置）。混在一起会两头不讨好。

### 定位信息的形态（中枢要产出的东西）

中枢对每个故障能力产出一份**结构化定位报告**，至少包含：

```
{
  "asset_id": "mcp::obsidian-suite",
  "failure_class": "launch_path_missing",
  "location": { "field": "mcpServers.obsidian-suite.command",
                 "value": "D:\\.my-agent\\.plugin\\obsidian-agent\\mcp\\.venv\\Scripts\\python.exe",
                 "source_file": "vendor/plugin/obsidian-suite/mcp.json" },
  "evidence": "该路径不存在；当前项目根为 C:\\work\\capability-core",
  "prerequisites": ["需要知道该 MCP 的正确 venv 位置"],
  "suggested_repair_kind": "path_remap",
  "repairable_by": "agent"
}
```

**关键**：`failure_class` 与 `evidence` 必须可复核（实测过），`suggested_repair_kind` 是**建议**不是命令——最终由智能体决定。

### 已知的故障分类（从实测得来）

| 类别 | 实例 | 中枢能定位到什么程度 |
|---|---|---|
| `launch_path_missing` | matlab-mcp-server、mineru×2、obsidian×3 | 能精确到字段与值，并说明路径不存在 |
| `unexpanded_var` | knowledge-process-suite、Presentations | 能指出变量名 `${QODER_NODE_RUNTIME}`，但**不知道该填什么** |
| `command_not_in_path` | mcp-for-blender (`uvx`) | 能指出命令不在 PATH，可提示需安装 uv |
| `dead_root` | 引用 `.my-agent`（改名前的根） | 能识别并推断是新旧根目录差异 |

### 多智能体接入的演进

维修不是单个智能体的事——**多个智能体可能同时发现同一个故障、或分别修不同能力**。需要：
1. 故障任务的**认领**机制（谁来修这条），避免重复劳动或互相覆盖
2. 修复动作的**审计**（谁在何时改了什么，失败可否回滚）
3. 修完后的**复核**（中枢重测，通过才算纳管成功）

这复用了已有的 `agents` / `agent_capability_usage` 表与身份裁剪机制。

**实测证据**：
- `skill::mcp-zotero-mcp` → HTTP 200，**6,581 字节**，与磁盘 `SKILL.md` 字节数完全一致
- `?max_bytes=100` → `returned=100, truncated=true, bytes=6581`
- `../../../etc/passwd` → **404**（路径穿越被拒）
- 不存在 id → 404（**不泄露存在性**）

**过程中修掉的一个真 bug（重要教训）**：

第一版实现**恒 404**。定位过程：
```
normalize-only => Some("D:\capability-core\vendor\mcp\zotero-mcp\SKILL.md")   ← 路径解析正确
resolve        => None                                                      ← 但被判越界
```
根因：防穿越判断写的是 `normalized.starts_with(db_parent)`，但 `source_path` 存的是 `..\vendor\...` —— **`..` 会把 `db_parent` 自己消掉**，于是每一次**合法**读取都被判成越界。

> 症状是「全文接口恒 404，而路径本身明明是存在的」。只看代码，这段防穿越看起来完全正确。

修正后：**拒绝绝对路径**（不合理数据），**允许 `..`**（库里存的就是相对路径），规范化后仍须是绝对路径。

## 2. 模块划分与解耦纪律

```
ac-core  协议层：零 IO、零依赖、零其他 crate 依赖
   ▲   ▲   ▲   ▲   ▲
   │   │   │   │   └── ac-ipc        只做类型转换
   │   │   │   └────── ac-mcp         MCP 服务端 + 多智能体协同
   │   │   └────────── ac-llm         叶子节点，谁都不依赖它
   │   └────────────── ac-retrieval    通过 trait 抽象存储后端
   └────────────────── ac-registry     存储实现
```

### 硬性约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | ac-core 不依赖任何 crate，不做 IO | 协议层必须最稳定，任何上层改动都不许动它 |
| 2 | **ac-retrieval 不直接依赖 ac-registry** | 二者通过 trait 通信。检索算法要能脱离 SQLite 单独测试，也能换存储后端 |
| 3 | ac-llm 是叶子节点 | 模型接入是可选能力，不能污染其他模块 |
| 4 | 禁止循环依赖 | Cargo workspace 强制 |
| 5 | 上层不得修改 vendor/ 下的外部资产 | 你明确要求不影响现有插件运行 |

### 耦合点清单（唯一允许的跨 crate 交互）

| 边界 | 接口 | 方向 |
|---|---|---|
| registry → retrieval | `AssetStore` trait | retrieval 定义 trait，registry 实现 |
| retrieval → llm | `Router` trait | retrieval 定义，llm 提供实现 |
| mcp → retrieval | `Searcher` trait | mcp 定义，retrieval 实现 |
| ipc → core | 直接用类型 | 无额外抽象 |

### M1.5 去重 ✅ 已实现（2026-10-16 落地，M1 收尾同时完成）

**目标**：把 506 条资产里的"内容相同、位置不同"的副本折叠成一份"逻辑资产 + N 个位置"，
但**不静默合并**——同内容多位置可能是用户故意为之，要给用户选择权。

#### 1. 重复来源（M1 实测 4 类）

| 来源 | 真实案例 | 用户意图 |
|---|---|---|
| **包多版本** | `architecture-visualization/0.1.0` 和 `1.0.0` 各自一份 SKILL.md | 故意保留——不同版本能并存 |
| **包多组件** | `architecture-visualization/skills/architecture-communicator/...` + `.../c4model/...` | 一个包不同功能组件，要保留 |
| **同包多副本** | `.skill/product-management` 和 `skill-pm-output-engine` 描述字符级一致 | **真重复**——需要去重 |
| **跨源镜像** | `vendor/skill/data-normalizer/...` 同时有 `plugin` 和 `skill` 两份 manifest | 重复——按 manifest 归一 |

#### 2. 三级指纹

| 级 | 算法 | 抗什么 | 例子 |
|---|---|---|---|
| L1 内容哈希 | 全文 SHA-256，忽略 frontmatter 头 | 字节级完全相同 | 重复文件 |
| L2 规范化指纹 | 去 frontmatter + 去空白 + 去版本号 + 小写归一 | 重打包/换格式 | "产品复盘" vs "产品 复盘" |
| L3 语义指纹 | 描述 + 能力声明 → MiniLM 嵌入（**M3 引入**） | 命名不同但功能相同 | "画时序图" vs "画流程图" |

**M1.5 只做 L1 + L2**。L3 必须等 M3 的向量基础设施，否则单独做就是给每个去重任务跑一次 embedding。

#### 3. 数据模型：逻辑资产 + 位置集

```text
LogicalAsset     <- 1 个
  content_hash   (L1)
  canonical_id   (按 content_hash 取最短那条 path)
  AssetKind
  name / version / description (取 canonical 那份)

AssetLocation    <- N 个
  logical_id     (FK)
  source_path    (真实磁盘位置)
  role           (canonical | alias)
  last_seen_at   (扫描时间戳)
```

**关键纪律**：
- 扫描输出**只增不删**：旧位置保留为 `alias`，便于"上次还是这版、现在升级了"的追溯
- id 不再带 `path-hash` 后缀：`architecture-visualization-0-1-0-skills-c4model`
  → `architecture-visualization-0-1-0::c4model`（路径 slug + 能力名）
- 多版本共存：每个版本是独立 logical asset，**不**用 `latest` 兜底
  ——"latest"是用户决策，不是程序决策

#### 4. UI 显式确认（绝不静默合并）

去重候选进入"待用户确认"队列，**必须**由用户在界面里勾选：
- 合并：去 alias、保留 canonical
- 共存：都升级为独立 logical asset
- 忽略：留在 alias 角色，等下次扫描再问

理由（用户原话）："多智能体使用工具过程中可能会产生变化或改动"
——静默合并会把"昨天改的本地定制版"和"今天拉的上游版"混成一份，
后一个智能体调到的就不是用户期望的版本。

#### 5. 迁移路径

| 阶段 | 数据库操作 |
|---|---|
| M1 末 | 新增 `logical_id` / `location_id` / `content_hash` 三列，**不删旧列** |
| M1.5 | 一次性脚本：`UPDATE assets SET logical_id = content_hash WHERE content_hash IS NULL` |
| M2 | UI 按 logical group 显示；旧 `id` 列保留 6 个月给回滚 |

#### 6. 与 M2/M3 的衔接

- M2 全文检索 → 命中 logical asset，去重后 N 个位置合 1 行
- M3 向量召回 → 同上；alias 召回时合并排序分数
- 多智能体协同（M5）→ 委派链里记录 logical_id + 具体 location，避免 A 智能体改了 location1 影响 B 智能体调 location2

#### 7. 实现记录（2026-10-16，代码已落地并验收）

**改了什么**

| 层 | 改动 |
|---|---|
| `ac-core` | 新增 `dedup.rs`：`LogicalAsset` / `AssetLocation` / `LocationRole` / `DedupCandidate` / `DedupDecision` / `MatchLevel`。仍是零 IO、零 crate 依赖。`Provenance` 加 `normalized_hash` |
| `ac-registry` | 新增 `fingerprint.rs`（L1+L2）；`store.rs` 加 `logical_assets` / `asset_locations` / `dedup_candidates` 三表 + `logical_id`/`location_id` 两列；`ingest.rs` 接上同步与候选生成 |
| `ac-retrieval` | **未改动**（仍是 M0 骨架，无 `AssetStore` trait，故不存在依赖方向问题） |
| 桌面端 | 新增 `list_tags` / `list_dedup_candidates` / `decide_dedup` / `dedup_history` 四个命令；界面加去重确认面板与标签筛选 |

**指纹：只做 L1 + L2，没有 L3**

- L1 = 去 frontmatter 后全文 SHA-256（前 8 字节）→ `logical_id = "l1-" + hash`，是分组**主键**
- L2 = 再去空白 / 去版本号 / 转小写后 SHA-256 → 只产出 `MatchLevel::L2` 候选，**永不自动合并**
