## 1. 测试策略

| 层级 | 手段 | 覆盖对象 | 运行方式 |
|---|---|---|---|
| **单元测试** | Rust 内联 `#[cfg(test)]` | 每个 crate 的纯逻辑 | `cargo test --release` |
| **契约测试** | Manifest 序列化往返 | 协议稳定性 | `ac-core` 集成测试 |
| **集成测试** | 跨 crate 链路 | 扫描→索引→检索 | `tests/` 目录（后续里程碑） |
| **性能基准** | `cargo bench` | 检索延迟、索引构建 | M2 引入 |
| **降级测试** | 故障注入 | 依赖不可用时的行为 | M3 引入 |
| **UI 测试** | WebView2 CDP 驱动真实 exe | 前端渲染、详情面板、点击交互 | **2026-10-17 启用**（见 §2.6） |

**原则**：单元测试必须能在**无网络、无数据库、无向量服务**的条件下跑完。

### 1.1 四层测试法（2026-10-17 确立，取代「穷举点击 506 条」）

上一轮的 UI 验证方式是**用 WebView2 CDP 逐条点击 506 项资产**。
它有两个无法接受的性质：

- 慢（逐条点击 + 每次等待渲染）
- **覆盖不全** —— 只验证了被点到的那 506 条里的每一条渲染，但**面板自身的逻辑
  （归一化、空数据分支、降级路径）一次都没被真正执行过**

因此改为四层。每一层只做它该做的那件事，不重复也不遗漏：

| 层 | 做什么 | 验证的是什么 | 实测耗时 |
|---|---|---|---|
| **第 1 层** | 数据层穷举：对库中全部 manifest 跑一遍 `normalizeManifest` | **数据没坏**。覆盖所有数据形态，不点 UI | **8 ms** |
| **第 2 层** | 分层抽样点击 ≤ 15 次 | **渲染链路真的通** | 约 40 s |
| **第 3 层** | 组件级单测（vitest + RTL + jsdom） | **面板自身逻辑 + 降级分支**，以后每次改前端秒级回归 | **2.4 s** |
| **第 4 层** | 冒烟：启动真实 exe | 端到端真实数据、控制台无报错、截图 | 约 5 min |

**耗时对比**：第 1 层 8 ms 覆盖 506 条数据，第 2 层 11 次点击覆盖渲染链路，
第 3 层 43 个用例覆盖面板逻辑与兜底分支。上一轮单是穷举点击就远超这个量级，
且**没有一项覆盖到降级路径**。

> **关键分工**：第 1 层答「数据对不对」，第 2 层答「渲染通不通」。
> 两者不可互相替代 —— 第 1 层再全也证明不了界面能画出来，
> 第 2 层点得再多也证明不了没点到的那 495 条数据是好的。

## 3. 缺陷与修复记录

### 3.1 BUG 1 · 点击资产详情黑屏（已修）

**根因**

Rust 侧 `ac-core` 对**空集合 / 空映射 / None** 一律加 `skip_serializing_if`，
序列化时**整个键被省略**。前端 `App.tsx` 却把 `provides` / `relations`
当成必有字段直接访问，`undefined.length` 抛 `TypeError` → React 渲染中断 →
整个窗口黑屏。

库里 506 条 manifest 的键频次实测（脚本 `artifacts/pre_keysurvey.py`）：

| 键 | 出现行数 | **缺失行数** |
|---|---|---|
| `provides` | 499 | **7** |
| `relations` | 18 | **488** |
| `identity.role` | 216 | 290 |
| `identity.dimensions` / `authority` / `side_effect` / `tool_posture` / `idempotent` / `open_world` | 506 | 0 |
| `provenance.*` 五个子键 | 506 | 0 |

> **影响面比最初定位的大。** 最初只报 `provides` 缺 7 条；
> 实测 `relations` 缺 **488/506**。也就是说即便把 `provides` 单独修好，
> 点任意一条资产仍会在 `manifest.relations.length` 上崩溃——**实际是"几乎必崩"**。
> 两处必须一起修。

7 条零能力资产（全部是 `plugin` 类的重打包壳）：

~~~
plugin::plugin-obsidian-suite-qoder-plugin
plugin::skill-data-normalizer-0-1-0-qoder-plugin
plugin::skill-moonbit-skills-0-1-0-claude-plugin
plugin::skill-product-management-1-1-1-qoder-plugin

**修复方式：只改前端，后端不动。**

1. **`src/types.ts`：把可选字段如实标成可选。**
   `CapabilityManifest` 的 `identity` / `provides` / `relations` / `provenance`
   全部改为可选。类型写必填只是骗 TS，运行时照样 undefined。
2. **`src/types.ts`：新增 `normalizeManifest()`（单一修复点）。**
   把任意来源的 manifest 归一化成字段齐全的 `NormalizedManifest`。
   null / undefined / 非对象 / 数组里塞非对象，全部降级为默认值，**绝不抛 TypeError**。
   渲染层从此只依赖归一化后的形状，不用在每个 JSX 表达式上散落 `?? []`。
3. **`src/App.tsx`：`Detail` 第一件事就是归一化**，
   之后所有访问都作用在 `NormalizedManifest` 上，由类型系统保证字段存在。
   零能力资产额外给一句"该资产未声明任何能力。"的空状态，而不是空白。

   列表行的 `authority_label` / `capability_count` 都做了缺失降级。
5. **加渲染错误边界（`RenderBoundary`）**：详情面板一层（按 `key={selected?.id}` 挂载，
   换资产自动重置），`main.tsx` 最外层一层。
   将来任何一处渲染抛错，降级成一块可见的错误卡片，其余面板照常可用——
   **不再有"一条坏数据抹掉整个窗口"这种失败模式**。

**为什么后端不改**（`provides` 是否应该永远输出空数组）

- 硬约束 `data/registry.db` 不得修改。库里 506 行**已经是省略 `provides` 的旧格式**。
  改 Rust 序列化只能影响**新写入**的行；存量行不重扫就不会变。
  要让改后端真正生效，就必须全量重扫重写数据库——正好踩中禁止项。**单改后端修不了这个 bug。**
- `skip_serializing_if` 是这套 schema 一贯的契约，不是疏忽：
  `identity.rs` / `relation.rs` / `dedup.rs` / `manifest.rs` 共 14 处一致使用。
  只给 `provides` 开例外会让格式不一致；要一致就得全改，代价是数据库与
  `preview.json` 的序列化格式整体变化，影响面远大于收益。
- 责任边界：`serde` 省略的是"没有值"的键，**消费方必须能处理缺失**。
  `bridge.ts` 在预览模式里早就有 `(i.manifest?.provides ?? [])` 的防御，
  说明这个约定是已知的，只是 `Detail` 漏了。前端归位到同一约定才是正确分层。
- 风险：改后端会牵动与 manifest 往返一致性相关的单测，并使 `preview.json` 格式变化，
  需要连带重新生成快照。

> **若将来仍想统一格式**：正确做法是升 `schema_version` 并全量重扫重写，
> 而不是悄悄改 `provides` 一个键的序列化。届时前端防御**依然要保留**——
> 库里还可能有外部来源的 manifest。

### 3.5 BUG 4 · `bridge.ts` 块注释未闭合，B 通道在界面上是死的（已修）

**发现方式**：建立前端测试框架时 `tsc --noEmit` 报的错。
**点击 506 条永远发现不了** —— 因为没有任何一条资产的渲染路径会调用 `scanHeartbeats`。

**根因**：`bridge.ts` 第 374 行

~~~
/** B 通道：扫描共享心跳目录。**
export async function scanHeartbeats(): Promise<HeartbeatScanReport> {

1. `OverviewPanel` 的「扫描心跳目录（B）」按钮导入到的值是 `undefined`，

3. 注释块内引用了 `HeartbeatScanReport` 类型，但那个 `import` 缺失 —— 同样被遮住了。

`HeartbeatScanReport` import。**未使用脚本做 read-modify-write。**

### 3.6 BUG 5 · 协议矩阵把 506 条全判成「源文件已不存在」（已修）

**发现方式**：第 4 层冒烟，真跑 exe 打开「模型接入」侧栏。
**tsc、单测、代码审查看不出来** —— 它只在真实数据库上才暴露。

**症状**：协议矩阵显示 **通过 0 / 不通过 1017，SKILL.md 0%**，
三行协议的「主要原因」全部是「源文件已不存在」。

**根因**：`protocol.rs` 第 ④ 项检查用 `scan_root` 去 join `source_path`：

~~~rust
} else if !root.join(&a.source_path).exists() {
~~~

但入库时 `source_path` 记的是相对**库文件父目录**的路径，形如：

~~~
..\vendor\mcp\matlab-mcp-server\.mcp.json
~~~

而 `scan_root` 本身就是 `vendor` 目录。两者差一级，拼出来是
`vendor\..\vendor\...` 这种二次前缀，**506 条全部找不到**。

**这不是渲染 bug** —— 面板忠实地显示了内核给的错误数字。是**内核算错了**。

**修复**：`check_all` 新增 `path_base` 参数（取库文件的父目录），
两个基准都试，任一命中即算在。**已加回归测试**：

~~~rust
fn source_path_relative_to_db_parent_still_resolves() {
    // 钉住真实数据形态：..\vendor\skill\a\SKILL.md
    let checks = check_all(&r, Some(&root), Some(base)).unwrap();
    assert!(checks[0].passed, ...);
}
~~~

**修复前后对比**（真实库 506 条资产）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 通过 | **0** | **980** |
| 不通过 | **1017** | **37** |
| SKILL.md（frontmatter） | 0% | **100%** |
| `.mcp.json` | 0% | **100%** |
| `plugin.json` | 0% | 40% |

剩下 37 条不通过是**真问题**，不是误判：原因写着
「manifest 声明 1 项能力，capabilities 表只有 0 行」——
manifest 里声明的能力没有真正落库。这是另一个问题，本轮只如实呈现、未修。

> **教训**：这是「数字必须来自真实查询」这条纪律的最好注脚。
> 查询确实是真的，界面也如实显示了，但**结论是错的**。
> 只有拿真实数据库真跑一次才暴露 —— 单元测试和代码审查都够不着它。

### 3.7 附带修复：`normalizeManifest` 造出「幽灵能力」

`asRecord` 把数组里的非对象元素（`null` / 字符串 / 数字）映射成 `{}`，
于是 `normalizeManifest` 会凭空造出 `capability_id` 为空串的「幽灵能力」，
详情面板会渲染出空白行 —— 看起来像数据，比不渲染更糟。

**修复**：`provides` / `relations` 先 filter 掉非对象条目再 map。
已加单测 `数组里塞非对象 → 非对象条目被丢弃` 与
`relations 塞非对象 → 同样被丢弃`。

> 真实库当前无此类数据（506 条 manifest 全部结构合法），
> 因此这是一条**防御性修复**，由畸形输入单测驱动，不影响现有显示。

### 本轮修掉的两个真 bug

**① 全文接口恒 404（路径解析缺陷）**

- 症状：所有合法 id 都返回 404，而路径本身存在
- 根因：防穿越用 `normalized.starts_with(db_parent)`，但 `source_path` 是 `..\vendor\...`，`..` 会把 `db_parent` 消掉 → 每次**合法**读取都判越界
- 修法：拒绝绝对路径，允许 `..`，规范化后仍须是绝对路径
