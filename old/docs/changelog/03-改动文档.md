### 2. 维修站诊断不再谎报向量层

`diagnostics.rs` 的 `check_vector` 曾硬编码输出「本仓库没有向量实现…向量层 absent」。
那句话在 M2 阶段属实，但 `ac-retrieval/src/vector.rs`（1852 行）落地后就成了**对外谎报**：
用户看到「没有实现」就不会去起嵌入服务，语义召回永远用不上。

改动：
- `DiagContext` 新增 `vector: Option<VectorProbe>`（absent/disabled/failed/ready 四态 + 端点/模型/维度/条数/原因）
- `VectorProbe::probe_from_env()` —— **真探一次**（放 ac-registry 而不是各调用方，保证 Tauri/HTTP/MCP 同一判据）
- `check_vector` 四态分开说，每档都给「用户下一步能做什么」；**未探测 ≠ 缺席**，两者文案不同
- `VectorProbe::failed()` 用 `assert!` 守住「failed 必须带原因」

**实测输出**（`cargo run --release -p ac-registry --example diag_probe`）：
```
[未探测（调用方没提供）]  info     向量层未探测
[真探（probe_from_env）]  warning  向量层故障（已自动降级）
   嵌入服务不可用（http://127.0.0.1:18191）：连接被拒绝 (os error 10061)
```

守门测试（**已做变异验证**：把 `match probe.state` 改成 `match "absent"` 后立刻红）：
`vector_diagnostic_reflects_each_state_instead_of_hardcoding_absent` /
`unprobed_vector_is_reported_as_unprobed_not_absent`

### 4. 修复任务栏图标（用户点名）

**根因（查 tauri-build 2.7.3 源码确认）**：exe 的 `RT_ICON` / `RT_GROUP_ICON` / `RT_VERSION`
**只能由 `tauri_build::build()/try_build()` 的 windows 分支**产出——它内部用
`tauri_winres::WindowsResource` 编译 .rc，同时写 manifest、icon（`set_icon_with_id`）与 version info
（`tauri-build-2.7.3/src/lib.rs:793-876`）。

本项目 `build.rs` **从未调用 tauri_build**，只自己拼了两个链接器开关
（`/MANIFEST:EMBED` + `/MANIFESTINPUT`）。那两个开关解决了启动崩溃（0xC0000139），
但**只管 manifest**，所以图标和版本信息全缺。

| 项 | 改动 |
|---|---|
| `apps/desktop/src-tauri/build.rs` | 改用 `tauri_build::try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest().app_manifest(<manifest>).window_icon_path("icons/icon.ico")))`；**删除手写链接器开关**（两者不能叠加，否则 manifest 重复 → 链接冲突或运行时读到旧那份） |
| `apps/desktop/src-tauri/icons/` | 新建。16/24/32/48/64/128/256/512 PNG + `icon.png` + `128x128@2x.png` + 多尺寸 `icon.ico`（7 档，29,619 B） |
| `tauri.conf.json` | `bundle.icon` 数组 + `publisher` / `copyright` / `shortDescription` / `longDescription` |

**关键坑**：
- Tauri 2 的 window 配置**没有 `icon` 字段**（加了 tauri-build 会报 unknown field）。窗口图标由
  `generate_context!` 调 `default_window_icon_from_app_icon_resource()` 从 **exe 资源**读
  （`tauri-2.12.4/src/image/mod.rs:61`），所以只要 exe 里有 RT_GROUP_ICON id=32512 就够了。
- PIL 的 ICO 保存：`sizes` 会对**同一张源图**逐档重采样，`append_images` 才对每档用专门图。
  想让 16px 用简化形态，必须用 `append_images` 精确匹配尺寸。

**图标设计**：六边形（能力核心/容纳）+ 三道竖条（skill/mcp/plugin 汇聚）+ 底部横梁（统一收拢）。
小尺寸（16/24/32）单独绘制简化形态（厚六边形环 + 单横梁），保证任务栏可辨识。

**验收**：
```
RT_ICON        count=7 ids=[1..7]
RT_GROUP_ICON  count=1 ids=[32512]
RT_VERSION     count=1 ids=[1]
ProductName=capability-core  FileVersion=0.1.0  Company=Capability Core Project
```
- 任务栏：运行中窗口 `WM_GETICON ICON_SMALL2` 返回真实图标句柄（32×32），截图确认是我们的图标
- Shell 提取：`ExtractIconEx` 返回 1 个图标、large 32×32 / small 16×16

### 5. 修掉启动红条「数据库未打开」

**现象**：每次启动界面顶部会闪一条红条「数据库未打开」，1 秒后自己消失；
而状态栏同时显示「506 条记录」——**自相矛盾**。

**根因**：后端 `open_registry` 是显式命令，App 首屏 effect 里才调它；
但 `OverviewPanel` / `RepairPanel` 在自己的 `useEffect` 里就发 `listAgents()` / `diagnostics()`，
**不保证排在 openRegistry 之后**。所有需要库的命令都用
`guard.as_ref().ok_or("数据库未打开")?` 硬拒。

**改法**：在 Tauri `setup()` 里**启动即打开库**（打开失败只打日志不 panic——
库坏了仍要能开窗口、让用户在维修站里看到原因）。前端 `openRegistry()` 保留（幂等），
但不再承担「必须最先跑」的时序责任。

**验收**：重启后红条消失，总览直接显示 6 个已登记智能体 / 19 条能力归属（真实数据，非占位）。

### 6. 新增 `examples/diag_probe.rs`

打印向量层诊断的两种形态（未探测 / 真探）。已登记进 `db_safety_guard::WATCHED`——
它强制显式 `--db`，没有默认到用户库的路径。

## v0.2.0 — M1 资产注册（2026-10-16）

### 目标

把 `vendor/` 下 508 个异构资产变成结构化 manifest 并入库，
界面上可浏览、可筛选、可查看身份维度。

### 新增模块

| 文件 | 职责 | 行数量级 |
|---|---|---|
| `kernel/crates/ac-registry/src/frontmatter.rs` | YAML frontmatter 最小解析器（**刻意不用 serde_yaml**：已废弃，触发 clippy 告警） | ~300 |
| `kernel/crates/ac-registry/src/infer.rs` | L4 身份推断：已知工具基线表 + 标签扫描 + 动词扫描 + 维度推断 | ~330 |
| `kernel/crates/ac-registry/src/parse.rs` | 三种格式解析 + `IdScope` id 生成 + `slugify` | ~560 |
| `kernel/crates/ac-registry/src/store.rs` | SQLite 存储、schema 迁移、列表查询、增量判定 | ~900 |
| `kernel/crates/ac-registry/src/scan.rs` | 两阶段目录扫描、相对根跳过、id 冲突消歧 | ~280 |
| `kernel/crates/ac-registry/src/ingest.rs` | 扫描→入库编排 + 全量对账 | ~200 |
| `kernel/crates/ac-registry/src/testutil.rs` | 测试临时目录（锚在 `target/`，见 P12） | ~110 |
| `kernel/crates/ac-registry/examples/ingest_vendor.rs` | 建库 CLI + 浏览器预览数据导出 | ~180 |

### ac-core 扩展

给 `Authority` / `SideEffect` / `ToolPosture` 补 `as_str()` / `label_zh()` / `parse()`，
字符串形式与 serde 的 `snake_case` **必须一致**——库表里存的就是这个字符串。

### 依赖新增

`rusqlite 0.32 (bundled)`、`sha2 0.10`、`walkdir 2`。
SQLite 走 bundled 是为了免去目标机器装 SQLite。

### 关键设计决策

| 决策 | 理由 |
|---|---|
| id = `<kind>::<相对扫描根的目录路径 slug>` | 叶目录名会大量重复（`.qoder-plugin` 被 22 个插件共用），导致 78 个资产被静默覆盖 |
| 同目录多份同类清单 → 追加 6 位短哈希 | `.mcp.json` 与 `mcp.json` 并存时无法区分；**冲突组全体都打标签**，保证以后新增文件不会改动已有 id |
| 跳过目录检查只作用于**相对根**的路径段 | 检查绝对路径时，扫描根落在 `target/` 下会导致整棵树被跳过 |
| `slugify` 保留 Unicode 字母数字 | 只留 ASCII 会把中文目录名整个丢掉，7 个中文技能挤进同一 id |
| 迁移以**实际列形状**判定，不看 `user_version` | 早期版本从未写过 `user_version`，真老库的版本号也是 0 |
| 新增 `PARSER_REV` 参与增量判定 | 只看 `content_hash` 时，改了解析逻辑老资产永远不刷新 |
| 身份偏序枚举拆成独立列 | M2 检索过滤要下推到 SQL，不能每行反序列化 JSON |
| 权限过滤在 SQL 里用 `CASE` 映射成等级 | 字符串字典序 `destructive < observe < read < write` 与枚举升序完全相反 |
| 扫描失败时不做全量对账 | 否则目录临时不可见会把整库清空 |

### 本轮修掉的真 bug

按发现顺序，每条都已补回归测试：

1. **id 冲突吞掉 78 个资产** —— 叶目录名当 id
2. **中文目录名被 slugify 吃掉** —— 7 个中文技能共用一个 id
3. **扫描根含 `target` 时整棵树被跳过** —— 跳过检查误用绝对路径
4. **`user_version=0` 的真老库无法升级** —— 建索引报 `no such column`
5. **改了解析逻辑但老资产永不刷新** —— 增量判定漏了代码版本
6. **`"skills": "skills"` 字符串声明被忽略** —— 22 个插件能力为 0（修复后 19）
7. **MCP 展示名显示成 `0.1.1`** —— 清单常在版本目录里
8. **插件组件对象写法（`hooks: {PostToolUse: []}`）被漏掉** —— 只认数组
9. **`write` 标签被当成 Destructive** —— 升权过头
10. **测试共用临时目录导致并行竞态** + **系统 TEMP 在本环境不可写**

### 已知限制（移交后续里程碑）

- 19 个 `.claude-plugin` 插件能力为 0：组件在同级目录，清单未内联声明 → 归属 M2 组件解析器
- vendor 存在同包多副本，内容相同 → 内容级去重策略待定，留到 M2 用 `content_hash` 折叠
- 扫描吞吐 34 项/秒，低于 200 的目标 → M2 改增量 + tantivy 后复测
- Tauri GUI 进程在当前执行沙箱内无法启动，exe 的 IPC 路径**未做运行时验证**（编译与命令签名已验证）

### ac-core 核心类型

新增三个模块：

**`manifest.rs`** —— 六类资产统一抽象
- `AssetKind`：Skill / Mcp / Plugin / Suite / Ghost / Organization
- `CapabilityManifest`：id、kind、name、version、description、identity、provides、relations、provenance
- `ProvidedCapability`：capability_id、name、summary、input_schema、tags
- `Provenance`：source_path、imported_at、content_hash、source_format
- `validate()` / `parse()`：ID 非空、名称非空、schema_version 匹配

**`identity.rs`** —— L4 多维身份（借鉴 Composio tag 模型 + ADCS 收窄语义）
- `Authority`：Read < Observe < Write < Destructive（可比较偏序）
- `SideEffect`：None < LocalArtifact < Mutating < Irreversible
- `ToolPosture`：Pure < Reader < Writer < Gated
- `CapabilityIdentity`：role + 三个偏序枚举 + idempotent + open_world + 自定义 `dimensions`
