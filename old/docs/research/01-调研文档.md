## 2. 关键设计借鉴详解

### 2.1 Composio 的三层筛选 → 我们的 L4 身份维度

Composio 的 Tool Router 用三层筛选控制一个智能体能拿到什么：

```typescript
composio.create(agentId, {
  toolkits: ['gmail', 'slack'],           // 第1层：能力集白/黑名单
  tools: { gmail: ['fetch', 'send'] },    // 第2层：工具级细粒度
  tags: ['readOnlyHint', 'idempotentHint']// 第3层：行为标签
});
```

其中 `tags` 的取值域是：`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`。

**我们把这个模式内化成 `CapabilityIdentity`**（`kernel/crates/ac-core/src/identity.rs`），
并做了两处扩展：

| Composio | CapabilityCore | 理由 |
|---|---|---|
| 4 个固定 hint | `Authority` 四级枚举（Read/Observe/Write/Destructive） | 需要可比较的偏序，用于委派链校验 |
| 平铺 tag | `tool_posture` 独立枚举（Pure/Reader/Writer/Gated） | 姿态与副作用是两个正交维度，不能混 |
| 无扩展 | `dimensions: BTreeMap<String,String>` | 领域、成本等自定义维度，且**可被结构化过滤**而非塞进向量 |

### 2.2 ADCS 委派链 → 我们的 L5

ADCS（Agentic Control Plane 发布的开放规范）的核心断言：
> 每条委派链的**根节点必须是一个人类**，能力沿链逐跳收窄，权限取各层交集。

我们的实现放在 `identity.rs::admits()`：

```rust
pub fn admits(&self, required: &CapabilityIdentity) -> bool {
    if self.authority < required.authority { return false; }
    if self.side_effect < required.side_effect { return false; }
    if required.tool_posture > self.tool_posture { return false; }
    for (k, v) in &required.dimensions {
        match self.dimensions.get(k) {
            Some(mine) if mine == v => {}
            _ => return false,
        }
    }
    true
}
```

对应测试 `authority_must_cover` / `dimension_mismatch_rejected` 已在 ac-core 中实现。

### 2.3 NVIDIA NeMo 的检索成本数据 → 我们的四级瀑布

NeMo-Retriever 实测（arXiv:2610.05750）：

| 方案 | nDCG@10 | 单次耗时 | Token |
|---|---|---|---|
| 单遍向量检索 | 基线 | 0.67s | 低 |
| ReAct Agentic | **+8.7 分** | **107.4s** | **76.4 万输入** |

**+8.7 分要付出 160 倍延迟和 76 万 token。** 这个数字直接决定了
我们不能只有向量检索，也不能让 LLM 做默认路由。

因此四级瀑布（见 `02-规划文档` M3）：
① Rust 全文 → ② 向量语义 → ③ 融合排序 → ④ LLM 判定（消歧，非默认）

## 4. 全网空白点（本项目的差异化）

调研发现，**L5（智能体编队）与 L4（执行过程身份）没有任何现成方案覆盖**：

| 空白 | 说明 |
|---|---|
| L5 智能体编队 | 现有多智能体框架（CrewAI/LangGraph/AutoGen）有**运行时编排**，但没有**可持久化、可索引、可查询的编队注册表** |
| L4 身份索引 | `SKILL.md` 规范里**没有身份字段**；MCP 没有；plugin 没有。唯一绑定点是 agent 本身 |
| Plugin 跨厂商标准 | Claude Code 的 `.claude-plugin/plugin.json` 是私有的，Cursor 的 plugin 也是专有的 |

## 7. 扫描 / 索引方案横向对比（M2 输入）

> 上一轮只写了一个方案的扫描速度（SQLite `LIKE` + 顺序解析），没横向对比。
> 这次把 4 个候选放在同一张表里看，再下选型。

### 7.1 语料量级（M1 实测，2026-10-16）

| 维度 | 数值 |
|---|---|
| 资产总数 | 506（隔离后；隔离前 508） |
| 清单文件总大小 | 6.6 MB（506 个文件累加） |
| 描述总字符 | 145,945（约 146 KB） |
| 清单 JSON 全部展开 | 610 KB（≈ 1.8 MB UTF-8） |
| 能力声明总数 | 518 条 |
| 能力数/资产 | 平均 1.02 |
| 扫描耗时 | ~15s（含分类、解析、SQL 写入；纯 IO ≈ 7s） |
| 现状 | 单进程、纯 Rust、SQLite 元数据索引；零检索后端 |

**结论先抛**：语料只有 ~2 MB，连 SQLite `LIKE` 都比 Elasticsearch 慢不了多少。
在这一量级，"上重型检索引擎"是**反向优化**。
但**M3 混合检索**会引入 30 万+ token 的工具池，那时候再换——现在就把接口留好。

### 7.2 方案候选

| 方案 | 形态 | 适用量级 | 当前 2 MB 耗时 | 100 MB 预估 | 优 | 劣 |
|---|---|---|---|---|---|---|
| **A. Rust 纯 SQLite + 顺序扫描** | 单进程库、零依赖 | < 10 MB | ~15s | ~60s | 零部署、零成本、可重入 | 无全文倒排、无向量、LIKE 慢 |
| **B. Rust + tantivy** | 内嵌 FST+倒排 | 10 MB – 10 GB | ~8s（首次建索引 ~25s） | ~3s | 全文 BM25、增量、纯 Rust | 多 ~30 MB 二进制、首次索引慢、没向量 |
| **C. Python + Whoosh / SQLite FTS5（外进程）** | 子进程 RPC | 10 MB – 1 GB | n/a（要部署 Python） | ~5s | 工具生态成熟、调试简单 | 启动 ~400 ms、跨语言、版本管理痛 |
| **D. 向量 RAG（Qdrant / LanceDB）** | 独立服务或嵌入式 | > 100 MB 文本 | n/a | n/a | 语义召回、扛规模 | 需 embedding 模型、首次入向量 ~5min、协议复杂 |

### 7.3 选型结论

| 阶段 | 方案 | 触发条件 |
|---|---|---|
| **M1（当前）** | **A** | 资产 < 1000、文本 < 2 MB，LIKE 够用 |
| **M2** | **A + 索引视图**：保留 A，**加 1 个倒排表 `capability_fts`**（FTS5 已在 SQLite 里，零外部依赖） | 资产上 1k、查询延迟 > 50 ms |
| **M3** | **A + B + D 渐进引入**：tantivy 做全文、向量做语义兜底 | 资产 > 5k、开始出现"工具名记不清要搜意思"的场景 |

**关键纪律**：
- 检索层（ac-retrieval）**不**直接持有 SQLite，**只**持有 `AssetStore` trait。
  换 B/D 不用改 retrieval 一行代码——这是 02-规划文档第 2 节硬性约束 #2 的兑现。
- 倒排和向量都**懒建**：首次查询触发，失败不致命，背景跑进度。
  不能让索引构建阻塞主链路，这和"扫描失败不删库"是同一条原则。
- 全文和向量**不互替**：BM25 命中"sketch"和"drawio"得分高，向量命中"画图"得分高，
  两个分数加权融合是 M3 唯一正确答案。

### 7.4 否决记录

| 候选 | 否决理由 |
|---|---|
| Elasticsearch / OpenSearch（自建） | 部署成本与本项目"本地优先"完全冲突；M1 阶段语料只有 2 MB |
| Meilisearch | 跨语言、嵌入式版本功能阉割；和 tantivy 比没明显优势 |
| pgvector | 强依赖 PostgreSQL；本项目选 SQLite 的核心理由就是"无服务" |
| Chroma | 要单独跑一个服务；M1 没人在乎多那 5s 延迟，换来的是部署噩梦 |
| Milvus | 集群方案，量级差 4 个数量级 |
| **LlamaIndex / LangChain 整套接进来** | 业务逻辑被框架绑架；只能"调用"，没法"换" |
